## Context

`backend/gateway` — пустой Spring Boot 4 проект (Java 17, Maven), уже содержащий зависимости `spring-boot-starter-security` и `spring-boot-starter-webmvc` (см. `backend/gateway/pom.xml`), но без единой конфигурации, контроллеров или сущностей. Рядом уже существует первый реальный backend-сервис `backend/tracker` (тоже пустой Spring Boot webmvc проект), который станет первым потребителем маршрутизации. Postgres разворачивается отдельно от кода (нет docker-compose и другой инфраструктуры в репозитории) и на первом этапе используется как одна общая база для всех сервисов. См. `proposal.md` — Why/What Changes для мотивации; здесь фиксируются только технические решения.

## Goals / Non-Goals

**Goals:**
- Определить, как gateway хранит пользователей и обрабатывает регистрацию/логин на базе Spring Security + JWT.
- Определить механизм обратного проксирования на webmvc-стеке без Spring Cloud.
- Зафиксировать формат конфигурации маршрутов «префикс URL → backend-сервис» для первого этапа (tracker).
- Зафиксировать схему БД gateway в общем Postgres так, чтобы другие сервисы могли получить собственные таблицы/схему без конфликтов в будущем.

**Non-Goals:**
- Service discovery / динамическая регистрация сервисов (маршруты статические, из конфигурации).
- Refresh-токены, revoke/logout, восстановление пароля — не входят в первый этап (можно добавить отдельным изменением).
- Rate limiting, circuit breaker, retries на прокси-слое.
- Роли/права доступа (RBAC) — на первом этапе есть только аутентификация, авторизация по ролям не требуется.
- Изменения в `backend/tracker` — сервис используется только как цель маршрутизации, его внутренняя реализация не входит в это изменение.

## Decisions

### 1. Аутентификация: JWT (stateless), выдаётся gateway

Gateway подписывает JWT access-токен собственным секретом (HMAC, симметричный ключ из конфигурации/переменной окружения) после успешного логина. Токен несёт `sub` (id пользователя) и `exp`. Для валидации входящих запросов gateway использует свой же секрет — не требуется отдельный auth-сервис или обращение к БД на каждый запрос.

Альтернатива — серверные сессии с хранением в Postgres/Redis и cookie — была рассмотрена и отклонена: с ростом числа сервисов stateless JWT проще масштабируется, а сессии требуют либо общего хранилища сессий, доступного всем сервисам, либо постоянного обращения к gateway за проверкой, что добавляет задержку и связанность. Пользователь подтвердил выбор JWT.

Downstream-сервисы (например, tracker) не проверяют подпись JWT самостоятельно на первом этапе — они доверяют заголовку с id пользователя, который добавляет gateway после успешной проверки (см. решение 3). Если в будущем появится прямой доступ к сервисам мимо gateway, эту границу доверия нужно будет пересмотреть — сейчас это осознанно вне рамок non-goals.

### 2. Роутинг: собственный reverse-proxy контроллер на webmvc

Гейтвей реализует единый catch-all контроллер/фильтр на базе `RestClient` (или `RestTemplate`), который:
1. Сопоставляет путь запроса с префиксом из статической конфигурации маршрутов (`gateway.routes[].prefix` → `gateway.routes[].target-base-url`).
2. Строит новый запрос к целевому base URL, сохраняя оставшуюся часть пути, query-параметры, метод и тело.
3. Копирует заголовки, кроме зарезервированных gateway (`Authorization` заменяется на внутренний заголовок с id пользователя для защищённых маршрутов).
4. Возвращает клиенту статус и тело ответа сервиса без изменений.

Альтернатива — `spring-cloud-starter-gateway-mvc` — была рассмотрена: она даёт готовые predicates/filters и меньше кода маршрутизации, но добавляет зависимость от Spring Cloud BOM/release train, отдельную модель конфигурации (`RouteLocator`) и кривую обучения, избыточную для одного статического списка маршрутов на первом этапе. Пользователь подтвердил простой контроллер как более подходящий для старта; переход на Spring Cloud Gateway MVC можно рассмotreть отдельным изменением, если список маршрутов и требования (retry, circuit breaker) вырастут.

Маршруты `/auth/register` и `/auth/login` обрабатываются локальными контроллерами gateway и явно исключены из reverse-proxy сопоставления (см. `gateway-request-routing` spec, Requirement "Публичные маршруты аутентификации не проксируются").

### 3. Передача идентичности пользователя вниз по цепочке

После успешной проверки JWT gateway добавляет к проксируемому запросу внутренний заголовок (например, `X-User-Id`) с id пользователя из токена. Backend-сервисы читают этот заголовок вместо повторной проверки JWT. Это упрощает сервисы первого этапа (tracker и далее), но требует, чтобы сервисы были доступны только через gateway в доверенной сети — прямой внешний доступ к ним, минуя gateway, не предусмотрен на этом этапе.

### 4. Хранение пользователей: Spring Data JPA + Postgres, отдельные таблицы gateway

Gateway использует `spring-boot-starter-data-jpa` + `org.postgresql:postgresql` для хранения таблицы `users` (id, email — уникальный индекс, password_hash, created_at). Так как Postgres на первом этапе общий для всех сервисов, таблицы gateway используют явный префикс/схему (например, схема `gateway` или префикс таблиц `gateway_`), чтобы избежать конфликтов имён с таблицами будущих сервисов в той же базе. Пароль хешируется `BCryptPasswordEncoder` (уже доступен через `spring-boot-starter-security`).

Схема БД управляется миграциями (Flyway или Hibernate `ddl-auto=validate` + ручные миграции) — конкретный инструмент фиксируется в tasks.md как первая техническая задача, если ещё не выбран в проекте.

### 5. Конфигурация маршрутов — статический список в `application.properties`/YAML

Для первого этапа список маршрутов задаётся в конфигурации gateway как массив пар `prefix` → `target-base-url` (например, `gateway.routes[0].prefix=/tracker`, `gateway.routes[0].target-base-url=http://localhost:8081`). Это осознанно просто и не требует внешнего реестра сервисов; расширение до конфигурируемого/динамического реестра — возможное будущее изменение, но не часть этого этапа.

## Risks / Trade-offs

- **[Risk]** Доверие к заголовку `X-User-Id` без повторной проверки в сервисах → если сервис станет доступен не только через gateway, возможна подмена идентичности. **Mitigation**: держать backend-сервисы в приватной сети/недоступными снаружи напрямую; явно задокументировать это ограничение в README сервисов при их создании.
- **[Risk]** Общая база Postgres для всех сервисов увеличивает риск конфликтов схем и связанности сервисов через БД. **Mitigation**: изолировать таблицы gateway отдельной схемой/префиксом с первого дня; параметризовать JDBC-строку подключения, чтобы переход на выделенную базу для gateway в будущем не требовал изменения кода, только конфигурации.
- **[Risk]** Статический список маршрутов требует редеплоя gateway при добавлении нового сервиса. **Mitigation**: приемлемо для текущего масштаба (несколько сервисов на первом этапе); внешний конфиг-файл/переменные окружения позволяют менять список без пересборки кода.
- **[Risk]** Отсутствие refresh-токенов означает, что после истечения access-токена пользователю нужно логиниться заново. **Mitigation**: осознанный trade-off ради простоты первого этапа; зафиксировано в Non-Goals, можно добавить отдельным изменением.

## Migration Plan

Изменение затрагивает только новый код в `backend/gateway` (сущности, контроллеры, конфигурация) и не переносит существующие данные — миграция в смысле "откат данных" не требуется. Шаги развёртывания:
1. Поднять Postgres (вне репозитория) и передать gateway параметры подключения через переменные окружения/`application.properties`.
2. Применить миграцию схемы gateway (создание таблицы пользователей) перед первым запуском.
3. Задать секрет для подписи JWT через переменную окружения (не хранить в репозитории).
4. Задать статический список маршрутов (как минимум запись для `tracker`) в конфигурации перед запуском.

Откат: поскольку изменений в существующих данных нет, откат сводится к остановке новой версии gateway и (при необходимости) откату миграции схемы БД.
