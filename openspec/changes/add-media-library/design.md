## Context

Проект состоит из нескольких Spring Boot сервисов за gateway (`gateway`, `tracker`, `finance`), React-клиента и общей БД `my_life`, где каждый сервис ведёт свою таблицу истории Flyway и baseline поверх схемы gateway. Мотивация изменения описана в `proposal.md`, требования — в дельтах `media-library`, `web-media`, `gateway-request-routing` и `web-app-hub`.

Существующие сервисы `tracker` и `finance` задают шаблон: сервис не проверяет JWT, а получает идентификатор пользователя из заголовка `X-User-Id`, который проставляет gateway; валидация выполняется вручную в сервисах; ошибки возвращаются в конверте `{"message": "..."}`; фронтенд ходит в API через общий `request` с prefix-путями `/tracker`, `/finances`.

## Goals / Non-Goals

**Goals:**

- Добавить сервис `media` строго по существующему шаблону сервисов, чтобы инфраструктурные изменения были механическими и предсказуемыми.
- Хранить фильмы/сериалы, книги и игры в одной модели, чтобы добавление четвёртого вида не требовало новой таблицы и нового набора эндпоинтов.
- Переиспользовать на клиенте существующие паттерны вкладок, модальных форм и API-слоя.

**Non-Goals:**

- Оценки, даты начала/завершения, прогресс, количество страниц/серий, жанры, авторы, платформы.
- Импорт из CSV, статистика, поиск, фильтрация по статусу, пагинация и сортировка списка пользователем.
- Изменение вида записи после создания.
- Совместный доступ и публичные списки.

## Decisions

### Отдельный сервис `backend/media`

Новый модуль `backend/media` (Spring Boot, порт 8083, context-path `/media`, `media_flyway_schema_history`, миграции с `V2`), собранный по образцу `backend/finance`: те же зависимости `pom.xml`, тот же `Dockerfile` с `EXPOSE 8083`, `UserIdFilter` с атрибутом `media.userId`, `GlobalExceptionHandler` с конвертом `{"message"}`.

Альтернатива — разместить медиатеку внутри `backend/tracker` — отклонена: сервисы разделены по предметным областям, а смешивание потребовало бы менять таблицы и тесты трекера без пользы.

### Одна таблица `media_items` с колонкой `type`

Поля всех трёх видов совпадают, отличается только значение вида. Модель:

- `id BIGINT` — PK;
- `user_id BIGINT NOT NULL`;
- `type VARCHAR(16) NOT NULL` — `FILM` / `BOOK` / `GAME`;
- `title VARCHAR(200) NOT NULL`;
- `description VARCHAR(2000)` — `NULL`, если описание отсутствует;
- `status VARCHAR(16) NOT NULL` — `NOT_STARTED` / `IN_PROGRESS` / `COMPLETED`;
- `created_at`, `updated_at TIMESTAMP WITH TIME ZONE NOT NULL`.

Индекс `idx_media_items_user_id_type (user_id, type)` обслуживает список подвкладки. Значения перечислений хранятся строками (`@Enumerated(EnumType.STRING)`), как в `tracker`.

Альтернативы: три отдельные таблицы `media_films`/`media_books`/`media_games` — дублирование схемы, репозиториев и сервисов; таблица видов с внешним ключом — лишняя сущность для закрытого набора из трёх значений.

### API в стиле существующих сервисов

- `GET /media/items?type=FILM` — список записей пользователя, `type` необязателен, порядок по возрастанию `id`;
- `POST /media/items` — тело `{type, title, description, status}`, `201` и созданная запись;
- `PUT /media/items/{id}` — тело `{title, description, status}`, `200` и обновлённая запись;
- `DELETE /media/items/{id}` — `204`.

Внешние пути (`/media/items`) совпадают с context-path сервиса, как у `tracker`. Запись ищется через `findByIdAndUserId`, поэтому чужая запись неотличима от несуществующей (`404`). Валидация — в сервисе, вручную: `title` после `trim()` непустой и ≤ 200 символов, `description` после `trim()` пустой → `null` и ≤ 2000 символов, `type` и `status` обязательны при создании (`status` по умолчанию `NOT_STARTED`), неизвестные значения перечислений отклоняются. `type` при изменении не принимается.

### Клиент: одна общая вкладка-компонент на три вида

`MediaPage` повторяет алгоритм вкладок `TrackerPage` (константы порядка, `activeTab`, ленивое монтирование `openedTabs`, `aria-selected`). Вместо трёх почти одинаковых компонентов создаётся `MediaTab`, параметризованный видом записи и текстами (заголовок, кнопка добавления, пустое сообщение) — тот же приём, что `ActivityListTab` в трекере.

Смена статуса в списке делается нативным `<select>` с тремя вариантами: он доступен с клавиатуры и не требует отдельного меню. Формы создания и редактирования — общий `MediaFormModal` с полями названия, описания и статуса. Удаление — подтверждение внутри списка, как в `ActivityListTab`.

Состояние подвкладки (загруженный список) хранится в её компоненте, поэтому переключение вкладок не вызывает повторную загрузку; `MediaPage` передаёт `refreshToken` только при необходимости.

### Инфраструктурные изменения по существующему шаблону

- gateway: `gateway.routes[2].prefix=/media`, `target-base-url=${GATEWAY_MEDIA_BASE_URL:http://localhost:8083}`; маршрут защищён правилом `anyRequest().authenticated()` автоматически.
- nginx: точные `location = /media` и `location = /media/` отдают `index.html` (SPA), `location /media/` проксируется в gateway.
- `docker-compose.yml` и `docker-compose.no-postgres.yml`: сервис `media` с `depends_on` на `postgres` и `gateway` (healthcheck), `expose: 8083`, переменные `MEDIA_DB_*`, в варианте без postgres — `extra_hosts`.
- `.gitea/workflows/backend-tests.yml`: `media` в матрице сервисов; `docker-publish.yml`: сборка образа `my-life-media`.
- `readme.md` и `.env.example`: описание сервиса, маршрута и переменных.

## Risks / Trade-offs

- [Отдельный сервис добавляет нагрузку на сопровождение: больше контейнеров и CI-задач] → изменения механические и копируют `finance`; публикация и тесты уже параметризованы матрицей.
- [Порядок запуска: `media` делает Flyway baseline поверх схемы gateway] → `depends_on: gateway: condition: service_healthy` в обоих compose-файлах, как у `tracker` и `finance`.
- [Ограничения длины названия и описания (200/2000) могут оказаться малы для описаний книг] → ограничения централизованы в одном месте сервиса и могут быть увеличены отдельной миграцией без изменения API.
- [Смена статуса через `<select>` изменяет данные сразу, без явного сохранения] → при ошибке интерфейс возвращает прежнее значение и показывает сообщение; поведение покрывается тестом.
- [Дублирование разметки вкладок между `TrackerPage` и `MediaPage`] → осознанно: вкладки различаются содержимым и обработчиками; общий компонент потребовал бы менять проверенный трекер.
- [SPA-маршрут `/media` может конфликтовать с API-префиксом] → точные `location` для `/media` и `/media/` размещаются до префиксного `location /media/`, как это сделано для `/tracker` и `/finances`.

## Migration Plan

Порядок выката: собрать образ `my-life-media`, применить обновления gateway (маршрут) и web (nginx), затем поднять `media` — миграция `V2__create_media_items_table.sql` создаёт таблицу `media_items` при первом старте. Данные существующих сервисов не затрагиваются.

Откат: убрать маршрут `/media` из gateway и nginx, остановить контейнер `media`; таблица `media_items` может остаться без влияния на другие сервисы (при необходимости удаляется вручную).
