## Context

Текущий трекер (`backend/tracker`) хранит один вид активностей — привычки — в таблице `tracker_habits` с общими отметками в `tracker_habit_completions`. Эндпоинты `/tracker/habits` уже реализуют создание, редактирование, список на дату, историю и отметку/отмену выполнения; правила валидации, часовой пояс (`Europe/Moscow`) и изоляция по пользователю общие. Веб-клиент (`client/web`) имеет страницу `TrackerPage` с вкладками «Привычки» и «Статистика», компоненты `HabitsTab`, `HabitFormModal`, `StatisticsTab` и API-клиент `trackerApi`. См. `proposal.md` — What Changes для мотивации.

## Goals / Non-Goals

**Goals:**

- Ввести различие двух видов активностей (обязательные `HABIT` и необязательные `TASK`) без дублирования правил и логики.
- Дать пользователю отдельную вкладку «Задачи» с тем же поведением, что у «Привычек».
- Показывать оба вида в одной статистике с визуальным разделением.
- Сохранить обратную совместимость уже заведённых привычек.

**Non-Goals:**

- Разные наборы правил/валидации для типов: правила остаются общими.
- Принудительность/напоминания/уведомления и любые проверки «обязательности» на бэкенде.
- Изменения маршрутизации gateway (используется существующий префикс `/tracker`).
- Изменение/удаление активностей в существующем UI.

## Decisions

### 1. Одна сущность с полем типа вместо отдельной сущности

Добавляем enum `ActivityType { HABIT, TASK }` и колонку `type` в `tracker_habits`. Логика отметок, планирования и истории переиспользуется как есть.

- **Почему:** правила идентичны, раздельные сущности привели бы к дублированию сервисов, репозиториев и тестов.
- **Альтернатива:** отдельная таблица/сущность `tracker_tasks` — отклонена из-за дублирования; JPA-наследование — избыточно для одного различающего поля.

### 2. Тип передаётся в существующий API, отдельные маршруты не создаются

- `HabitRequest` получает поле `type` (`ActivityType`). При создании `type` обязателен; при редактировании приходящий `type` игнорируется, сохраняется текущий тип активности.
- `HabitResponse`, `HabitOnDateResponse`, `HabitHistoryResponse` получают поле `type` (сериализуется строкой, как `frequency`).
- `GET /tracker/habits` получает необязательный параметр `type`; при отсутствии — возвращаются оба типа.
- `GET /tracker/habits/history` возвращает оба типа с полем `type` (для общей статистики), дополнительный фильтр не вводится.
- Эндпоинты отметки/отмены выполнения не меняются и работают для обоих типов.

- **Почему:** единая точка логики, минимум изменений контракта, вкладки просто передают `type`.
- **Альтернатива:** `/tracker/tasks` как отдельный контроллер — отклонено из-за дублирования; тип в path-параметре — усложняет совместимость.

### 3. Миграция Flyway V3 c безопасным значением по умолчанию

`V3__add_tracker_habits_type.sql`: `ALTER TABLE tracker_habits ADD COLUMN type VARCHAR(16) NOT NULL DEFAULT 'HABIT'`. Существующие записи становятся `HABIT`.

- **Почему:** аддитивное изменение, не ломает данные и позволяет откат удалением колонки.
- **Альтернатива:** отдельная миграция данных + NOT NULL без дефолта — сложнее и не даёт выигрыша.

### 4. Общий React-компонент списка активностей, параметризованный типом

`HabitsTab` обобщается в переиспользуемый компонент (например, `ActivityListTab`) с проп `type` и текстами (заголовки, «Добавить привычку»/«Добавить задачу», пустое состояние). `TrackerPage` монтирует две вкладки: «Привычки» (`HABIT`) и «Задачи» (`TASK`). Обе панели после первого открытия остаются смонтированными, чтобы сохранять выбранную дату (как сейчас сделано для статистики через `statisticsOpened`). `HabitFormModal` получает проп `type` и отправляет его в `trackerApi.create`.

- **Почему:** одинаковое поведение без копирования; сохраняется существующее поведение вкладок.
- **Альтернатива:** отдельный `TasksTab` с копией кода — отклонён.

### 5. Статистика группирует строки по типу

`StatisticsTab` группирует записи истории по `type` (сначала `HABIT`, затем `TASK`) и добавляет строку-заголовок группы, пересекающую все столбцы, перед каждой группой. Легенда и подсветка квадратов не меняются.

- **Почему:** минимальная правка существующей матрицы, типы визуально различимы.
- **Альтернатива:** отдельные таблицы на тип — противоречит решению «одна матрица»; цветовая кодировка без подписи — хуже читается.

## Risks / Trade-offs

- Изменение поведения `GET /tracker/habits` при отсутствии `type` (теперь оба типа) → вкладки всегда передают `type` явно, а тесты обновляются под новое поведение; при необходимости можно вернуть дефолт `HABIT`.
- Сущность и capability по-прежнему называются «habit», хотя теперь покрывают задачи → сохраняем имена ради совместимости спек и минимального диффа, различие выражено полем `type`.
- Дублирование дат/состояния между двумя вкладками при переключении → обе панели остаются смонтированными после первого открытия, даты хранятся в своём компоненте.
- Ошибка сериализации enum → `type` используем как строку (`@Enumerated(EnumType.STRING)` и JSON по образцу `frequency`), покрываем интеграционным тестом контроллера.
- Рассинхронизация фронта и бэка при поэтапном деплое → API аддитивно (новое поле/параметр), старый фронт без `type` получит значения по умолчанию из миграции.

## Migration Plan

1. Выкатить tracker с миграцией V3 (аддитивная колонка с дефолтом `HABIT`) и новым API.
2. Выкатить web-клиент с вкладкой «Задачи» и типизированным API.
3. Откат: вернуть предыдущие версии сервисов; при необходимости удалить колонку `type` (данные привычек сохраняются).
