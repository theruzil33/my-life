## Context

Трекер хранит активности (привычки и задачи) в таблице `tracker_habits`, отметки — в `tracker_habit_completions`, дни недели — в `tracker_habit_weekdays`. Обе дочерние таблицы уже объявлены с `ON DELETE CASCADE` на `tracker_habits.id` (миграция `V2__create_tracker_habits_tables.sql`), поэтому удаление строки активности на уровне БД каскадно снимает её отметки и дни недели. Эндпоинт редактирования `PUT /habits/{id}` реализован и валидирует полное определение активности (название, дата начала, периодичность), но веб-клиент им не пользуется. В веб-клиенте вкладки «Привычки» и «Задачи» строятся на общем компоненте `ActivityListTab`, а список на дату (`HabitOnDateResponse`) уже возвращает полное определение активности: `startDate`, `frequency`, `weekdays`, `type`. См. `proposal.md` — Why; требования — в дельтах спек `tracker-habits` и `web-tracker`.

## Goals / Non-Goals

**Goals:**

- Дать пользователю переименовывать и удалять активности обоих типов в списках вкладок «Привычки» и «Задачи».
- Переиспользовать существующий механизм редактирования для переименования и существующие каскады БД для удаления, не расширяя модель данных.
- Сохранить изоляцию по пользователю: удалять и переименовывать можно только свои активности.

**Non-Goals:**

- Полное редактирование из UI (изменение даты начала и периодичности) — по решению пользователя переименование меняет только название.
- Мягкое удаление, корзина и восстановление — удаление безвозвратное.
- Новые эндпоинты для переименования и изменения маршрутизации gateway.
- Изменение схемы БД и новые миграции.

## Decisions

### 1. Удаление через БД-каскад, новый эндпоинт `DELETE /habits/{id}`

`HabitController` получает `DELETE /habits/{id}`, `HabitService.delete(userId, id)` вызывает существующий `requireHabit(userId, habitId)` (проверка владельца → `HabitNotFoundException` → `404`) и затем `habitRepository.delete(habit)`. Ответ — `204 No Content`. Отметки и дни недели удаляются каскадом БД; Hibernate сам очищает `@ElementCollection` дни недели при удалении сущности.

- **Почему:** минимум кода, изоляция владельца уже реализована в `requireHabit`, целостность обеспечивается внешними ключами.
- **Альтернатива:** явно удалять отметки через `HabitCompletionRepository.deleteByHabitId` перед удалением активности — дублирует каскад и требует нового метода репозитория без выигрыша.
- **Альтернатива:** мягкое удаление флагом `deleted_at` — отклонено, требует миграции и фильтрации во всех запросах.

### 2. Переименование переиспользует `PUT /habits/{id}`

Контракт API не расширяется: веб-клиент отправляет в существующий `PUT /habits/{id}` тело `HabitRequest` со **новым названием** и **неизменными** `startDate`, `frequency`, `weekdays`, `type`, взятыми из записи списка (`HabitOnDateResponse`). Бэкенд применяет обычную валидацию редактирования и сохраняет тип.

- **Почему:** переименование — частный случай редактирования; API уже поддерживает смену названия с корректной валидацией и сохранением отметок.
- **Альтернатива:** отдельный `PATCH /habits/{id}` с телом `{name}` — новое поведение и endpoint ради одной операции; отклонено.
- **Следствие:** UI обязан передавать расписание без изменений, иначе переименование могло бы его затронуть. Это покрывается интеграционным и unit-тестами.

### 3. Отдельный компонент окна переименования

Для переименования вводится лёгкий компонент (например, `RenameActivityModal`) с одним полем названия, предзаполненным текущим значением. Он не переиспользует `HabitFormModal`, чтобы не смешивать создание (дата, периодичность) с переименованием и не показывать лишние поля.

- **Почему:** проще и тестируемее, чем режимы в `HabitFormModal`.
- **Альтернатива:** обобщить `HabitFormModal` режимом редактирования — потянуло бы за собой поля расписания и противоречило решению «только название».

### 4. Подтверждение удаления — кастомное модальное окно

Подтверждение реализуется встроенным модальным окном в `ActivityListTab` (в стиле существующих модальных окон), а не `window.confirm`, чтобы сохранить единый UI и удобство тестирования.

- **Почему:** согласованность интерфейса и возможность управлять текстом, кнопками и блокировкой во время запроса.
- **Альтернатива:** `window.confirm` — нативный, но не стилизуемый и сложнее тестируется в jsdom.

### 5. Действия в строке списка и состояние ожидания

В каждом элементе списка рядом с названием появляются кнопки «Переименовать» и «Удалить». Ошибки переименования и удаления выводятся через существующий `actionError`. Во время запроса переименования или удаления соответствующие действия для этой активности блокируются (расширение существующего паттерна `pendingIds`).

- **Почему:** единый паттерн с отметкой выполнения (там уже есть `pendingIds` и `actionError`), минимум новой механики.
- **Альтернатива:** отдельные спиннеры/состояния на каждое действие — избыточно.

### 6. API-клиент: методы переименования и удаления

В `trackerApi` добавляются `update(token, id, definition)` (обёртка над `PUT /tracker/habits/{id}`) и `remove(token, id)` (обёртка над `DELETE`). Оба — изменяющие, поэтому `request` автоматически прикладывает access-токен и CSRF-токен; пустой ответ `204` корректно читается как `null`.

- **Почему:** существующий `client.js` уже обрабатывает CSRF/401 для `DELETE`/`PUT`.
- **Альтернатива:** прямой `fetch` в компоненте — обходит обработку токенов и ошибок.

## Risks / Trade-offs

- **Удаление безвозвратно стирает историю отметок** → обязательное подтверждение в UI и явные сценарии в спеке; пользователь подтвердил такое поведение.
- **Переименование через полный `PUT` может изменить расписание при ошибке в теле** → фронтенд передаёт `startDate`/`frequency`/`weekdays`/`type` без изменений; unit- и интеграционные тесты проверяют сохранение расписания и отметок.
- **Каскад полагается на внешние ключи БД** → каскады уже объявлены в миграции `V2`; интеграционный тест удаления с отметками проверяет фактическое поведение.
- **Расхождение фронта и бэка при поэтапном деплое** → бэкенд-изменение аддитивно (`DELETE` не ломает существующие вызовы); старый фронт продолжает работать без действий переименования/удаления.
- **Пустой ответ `DELETE` (`204`)** → `readBody` возвращает `null` для пустого тела, дополнительной обработки не требуется.

## Migration Plan

1. Выкатить tracker с новым `DELETE /habits/{id}` (аддитивный эндпоинт, миграции нет).
2. Выкатить web-клиент с действиями переименования и удаления.
3. Откат: вернуть предыдущую версию web-клиента (действия исчезают); `DELETE`-эндпоинт можно оставить, он не влияет на старое поведение.
