## Context

`backend/tracker` — пустой Spring Boot 4 проект (Java 17, Maven, `spring-boot-starter-webmvc` без персистентности), см. `backend/tracker/pom.xml` и `backend/tracker/src/main/java/com/theruzil/tracker/TrackerApplication.java`. Мотивация и объём изменения описаны в `proposal.md`; здесь фиксируются технические решения.

Ключевые внешние контексты, определяющие подход:

- Gateway уже реализован (см. `openspec/specs/gateway-request-routing/spec.md`). `ProxyRoutingFilter` формирует целевой URL как `target-base-url + request.getRequestURI()`, то есть префикс `/tracker` **не отбрасывается**: запрос `GET /tracker/habits` придёт в tracker с путём `/tracker/habits`. Для защищённых запросов gateway добавляет заголовок `X-User-Id` со строковым id пользователя (`ProxyRoutingFilter.USER_ID_HEADER`). Заголовок `Authorization` вниз не передаётся.
- Gateway использует общий PostgreSQL, таблицы изолирует префиксом `gateway_`, схема управляется Flyway с миграциями в `classpath:db/migration`, в тестах поднимает H2 в режиме PostgreSQL с `ddl-auto=validate` (см. `backend/gateway/src/test/resources/application.properties`).
- Стиль ответов об ошибках в проекте — `ApiError(String message)`, сериализуемый как `{"message": "..."}` (`backend/gateway/src/main/java/com/theruzil/gateway/web/ApiError.java`).
- `tracker` не содержит Spring Security и не проверяет JWT: он доверяет заголовку `X-User-Id` (осознанное решение gateway-этапа, см. archived design `2026-09-17-add-api-gateway-auth-routing`).

Пользователь подтвердил следующие поведенческие решения: «сегодня» определяется настраиваемым часовым поясом сервиса; отметка/отмена разрешена только для дат в диапазоне `[startDate, сегодня]`, совпадающих с периодичностью; при редактировании можно менять название, дату начала и периодичность, а сохранённые отметки не пересчитываются; список привычек и история доступны на произвольную дату и диапазон, включая прошлые; запрос даты (или начала диапазона) ниже самой ранней привычки пользователя даёт `400` с сообщением; будущие даты в списке и истории допустимы (в отличие от отметки выполнения).

## Goals / Non-Goals

**Goals:**

- Определить REST-контракт эндпоинтов привычек, их пути с учётом сохранения префикса `/tracker` gateway-ом и коды ошибок.
- Определить модель хранения привычек, периодичности и отметок выполнения в общем PostgreSQL с изоляцией по префиксу `tracker_`.
- Зафиксировать способ получения идентификатора пользователя и способ вычисления «сегодня» так, чтобы поведение было тестируемым.
- Зафиксировать стратегию тестирования (unit + интеграционные) в соответствии с правилом проекта из `openspec/config.yaml`.

**Non-Goals:**

- Изменения в `gateway` (проксирование, аутентификация, доверие к заголовку).
- Удаление привычек, архивирование, пауза/возобновление действия привычки — не запрашивались.
- Напоминания и уведомления.
- Аналитика поверх истории: стрики, проценты выполнения, агрегаты и графики. История отдаёт сырые статусы за явно заданный диапазон, но не считает по ним статистику.
- Часовой пояс пользователя в запросе: используется один пояс на сервис.
- Проверка JWT внутри tracker, RBAC и любые роли.
- Вынос `tracker` на отдельную базу данных: используется общая база проекта (как у gateway), с префиксом таблиц.

## Decisions

### 1. Пути эндпоинтов задаются через `server.servlet.context-path=/tracker`

Так как gateway сохраняет исходный путь, tracker должен принимать запросы с префиксом `/tracker`. Context-path настраивается в `application.properties`, а контроллеры используют ресурсные пути относительно него:

- `POST /habits` — создание привычки;
- `PUT /habits/{id}` — редактирование привычки;
- `GET /habits?date=yyyy-MM-dd` — список привычек, запланированных на дату, со статусом выполнения на эту дату; без параметра `date` используется сегодня;
- `GET /habits/history?from=yyyy-MM-dd&to=yyyy-MM-dd` — история: привычки со статусами выполнения за диапазон дат (включительно);
- `PUT /habits/{id}/completions/{date}` — отметить выполнение на дату;
- `DELETE /habits/{id}/completions/{date}` — отменить выполнение на дату.

Внешне через gateway это `POST /tracker/habits` и т.д.

Tracker слушает порт `8081` (`server.port=8081`, переопределяется через `SERVER_PORT`), потому что gateway по умолчанию маршрутизирует `/tracker/**` на `http://localhost:8081` (`gateway.routes[0].target-base-url`). Без явного порта tracker занял бы 8080 (порт gateway) и был бы недостижим через маршрутизацию.

Альтернатива — дублировать префикс `/tracker` в `@RequestMapping` каждого контроллера — отклонена: префикс повторялся бы в каждом новом контроллере и легко рассинхронизировался бы; context-path выражает «сервис смонтирован под своим префиксом» ровно один раз. Альтернатива — попросить gateway отбрасывать префикс при проксировании — отклонена, потому что изменение gateway вне рамок этого изменения.

### 2. Модель данных: `tracker_habits` + `tracker_habit_weekdays` + `tracker_habit_completions`

- `tracker_habits`: `id`, `user_id` (id из `X-User-Id`), `name`, `start_date DATE`, `frequency VARCHAR` (`DAILY` или `SPECIFIC_WEEKDAYS`), `created_at`, `updated_at` (TIMESTAMP WITH TIME ZONE). Индекс по `(user_id)`.
- `tracker_habit_weekdays`: `habit_id` (FK на `tracker_habits`, ON DELETE CASCADE), `day_of_week SMALLINT` (1–7, ISO), PK `(habit_id, day_of_week)`. Заполняется только для `SPECIFIC_WEEKDAYS`.
- `tracker_habit_completions`: `id`, `habit_id` (FK, ON DELETE CASCADE), `completed_on DATE`, `created_at`. Уникальное ограничение `(habit_id, completed_on)` обеспечивает идемпотентность отметки на уровне БД.

Периодичность моделируется парой «enum + дочерняя таблица дней недели», а не семью boolean-колонками или CSV-строкой. Альтернатива с битовой маской/CSV отклонена: невозможно выразить check-ограничения и неудобно фильтровать привычки на дату SQL-запросом.

Привычка «ежедневно» хранится как `frequency = 'DAILY'` с пустым набором недель; «конкретные дни» — как `frequency = 'SPECIFIC_WEEKDAYS'` с непустым набором. Валидация сервиса гарантирует согласованность (ежедневная привычка не имеет записей в `tracker_habit_weekdays`, а набор дней для `SPECIFIC_WEEKDAYS` непуст).

Схема создаётся Flyway-миграцией `V2__create_tracker_habits_tables.sql` (нумерация продолжает общий каталог проекта, чтобы не конфликтовать с `V1__create_gateway_users_table.sql`). `ddl-auto=validate`, как в gateway: схема принадлежит миграциям, а не Hibernate.

Так как gateway и tracker используют одну общую БД, но разные наборы миграций, они не должны делить таблицу истории Flyway: gateway оставляет стандартную `flyway_schema_history`, а tracker задаёт собственную `spring.flyway.table=tracker_flyway_schema_history`. Иначе валидация Flyway у tracker падает с «Detected applied migration not resolved locally: 1» на миграции gateway. Это обнаружилось при запуске против реального PostgreSQL (в H2-тестах у каждого сервиса своя БД, поэтому тесты проблему не ловили). Поскольку схема `public` к моменту первого старта tracker уже непустая (таблицы gateway), а отдельной истории ещё нет, tracker также включает `spring.flyway.baseline-on-migrate=true` с `baseline-version=1`: Flyway создаёт собственную историю, фиксирует базовую версию 1 и применяет `V2`. При пустой БД (тесты H2) baseline не срабатывает и миграции применяются как обычно.

Альтернатива — отдельная схема PostgreSQL для tracker (`spring.flyway.schemas=tracker` + `default_schema`) — отклонена как более инвазивная: она меняет имена схемы для JPA и требует согласованных правок во всех запросах/миграциях, тогда как отдельная таблица истории решает конфликт Flyway минимальной настройкой. Альтернатива — `ignore-migration-patterns=*:missing` — отклонена: оставляет общую историю, в которую пишут оба сервиса, что хрупко при росте числа сервисов.

Альтернатива — хранить данные привычек в базе gateway — отклонена: нарушает разбиение на сервисы по владению данными и создаёт связанность через БД, которую gateway-этап явно старался ограничить.

### 3. Получение идентификатора пользователя: сервлет-фильтр + атрибут запроса

`tracker` не подключает Spring Security. Вместо этого добавляется `UserIdFilter` (`OncePerRequestFilter`), который:

1. читает заголовок `X-User-Id`;
2. если заголовок отсутствует или не является числом — отвечает `401` с телом `{"message":"authentication required"}` и не пропускает запрос;
3. иначе кладёт `Long userId` в атрибут запроса.

Контроллеры получают значение через `@RequestAttribute`. Альтернатива — `@RequestHeader(value = "X-User-Id", required = false)` в каждом методе — отклонена: обработка отсутствующего заголовка размазывается по контроллерам, и легко получить 400 вместо требуемого спекой 401. Альтернатива — подключать Spring Security только ради извлечения заголовка — отклонена как избыточная зависимость без модели аутентификации.

Граница доверия: заголовок считается достоверным, потому что сервис доступен только через gateway. Это ограничение наследуется от gateway-этапа и выносится в README/конфигурацию сервиса, но не решается в коде.

### 4. «Сегодня» вычисляется через бин `Clock` с настраиваемым `ZoneId`

Вводится property `tracker.time-zone` (по умолчанию `Europe/Moscow`), из неё создаётся бин `Clock.system(zone)`. Все места, где нужна сегодняшняя дата/день недели (валидация при создании, дата по умолчанию для списка и истории, проверка диапазона и периодичности при отметке), используют `LocalDate.now(clock)`. Это делает поведение детерминированным в тестах: в тестах бин `Clock` заменяется на `Clock.fixed(...)`.

Альтернатива — `LocalDate.now()` напрямую — отклонена: зависит от часового пояса JVM и не поддаётся детерминированному тестированию. Альтернатива — часовой пояс в запросе — отклонена пользователем в пользу единого пояса сервиса.

### 5. Отметка/отмена выполнения: идемпотентные `PUT`/`DELETE` по дате

Дата выполнения — часть ресурса (`/completions/{date}`, формат ISO `yyyy-MM-dd`). Отметка — `PUT`: повторный `PUT` на ту же дату не создаёт новую запись (гарантируется уникальным индексом и upsert-семантикой сервиса). Отмена — `DELETE`: удаление несуществующей отметки завершается успешно и не меняет состояние.

Валидация даты (общая для отметки и отмены, выполняется до изменения данных): дата не в будущем относительно «сегодня» в настроенном поясе; дата не раньше `start_date`; день недели входит в периодичность привычки. Нарушения → `400` с сообщением; отсутствующая/чужая привычка → `404`.

Альтернатива — один эндпоинт с булевым флагом `completed` — отклонена: смешивает две разные семантики в одном запросе и хуже выражает идемпотентность.

### 6. Список на дату формируется SQL-выборкой, статус вычисляется join-ом

Дата списка разрешается параметром `date`; если он не передан, берётся `LocalDate.now(clock)` (см. решение 4). Выборка привычек на дату `:day`: `start_date <= :day` и (`frequency = 'DAILY'` или существует запись в `tracker_habit_weekdays` с `day_of_week = :dayDayOfWeek`), только для `user_id = :userId`. Признак выполнения на запрошенную дату получается `left join` с `tracker_habit_completions` по `completed_on = :day`. Будущие даты обрабатываются той же выборкой: она вернёт только привычки с `start_date <= :day`, поэтому отдельной ветки для будущего не требуется.

Перед выборкой сервис сравнивает запрошенную дату с самой ранней датой начала среди привычек пользователя (`MIN(start_date)` по `user_id`). Если дата раньше минимума — `InvalidHabitDataException` (`400` с сообщением), как того требует спека. Если у пользователя нет привычек, минимум не определён: список возвращается пустым без ошибки.

Альтернатива — загружать все привычки пользователя и фильтровать в Java — отклонена на будущее: список привычек растёт, а условие «день недели по периодичности» хорошо выражается индексом `(habit_id, day_of_week)`; при этом фильтрация в Java допустима как упрощение, если запрос окажется неудобным, — поведение спеки от этого не меняется.

Альтернатива — отдельный эндпоинт `/habits/{date}` вместо параметра запроса — отклонена: параметр `date` позволяет оставить один эндпоинт для сегодня и произвольной даты, а `/habits/today` становится избыточным (`/habits` без параметра уже означает сегодня).

### 7. История за диапазон отдаёт только запланированные дни

История (`GET /habits/history?from=&to=`) читает привычки пользователя, у которых есть хотя бы один запланированный день в `[from, to]` (`start_date <= to` и есть совпадение по периодичности), и join-ом подтягивает отметки из `tracker_habit_completions` в этом диапазоне. Ответ — по привычке массив записей `{date, completed}` только для дней, соответствующих периодичности привычки; дни вне периодичности не перечисляются, а привычки без запланированных дней в диапазоне в ответ не включаются. Это согласуется с семантикой списка на дату: «день есть в ответе» = «привычка запланирована на этот день».

Валидация границ выполняется до выборки: `from` позже `to` → `400`; `from` раньше самой ранней даты начала привычек пользователя → `400` (та же проверка, что и для списка на дату). Будущие границы допустимы; для них дни, не наступившие фактически, всё равно присутствуют в ответе как `completed = false`, поскольку ответ описывает расписание и отметки, а не «наступившее время».

Альтернатива — отдавать все календарные дни диапазона с явным статусом `not_scheduled` — отклонена: раздувает ответ и дублирует уже известную клиенту периодичность; при этом клиент может восстановить полную сетку из периодичности привычки. Альтернатива — вернуть отметки отдельным «плоским» списком без привычек — отклонена: пользователю нужен один запрос, который сразу даёт привычки вместе со статусами.

### 8. Валидация и ошибки: исключения домена + `@RestControllerAdvice`

Вводится `InvalidHabitDataException` (→ `400`) и `HabitNotFoundException` (→ `404`), обрабатываемые `GlobalExceptionHandler` в стиле gateway (`ApiError` с полем `message`). `400` используется в том числе для валидации дат списка и границ истории (`date`/`from` ниже самой ранней привычки, `from` позже `to`). Отсутствие/некорректность `X-User-Id` обрабатывается в фильтре (→ `401`), а не в advice, потому что отказ происходит до маршрутизации в контроллер.

Тело запросов/ответов — Java records в пакете `dto`. Форматы дат — ISO (`LocalDate`, формат `yyyy-MM-dd`); поле периодичности в запросе — `DAILY`/`SPECIFIC_WEEKDAYS` плюс массив дней недели; в ответе для удобства отдаются и `frequency`, и список дней недели, и признак выполнения на запрошенную дату. Ответ истории — по привычке массив записей `{date, completed}` за запланированные дни диапазона.

### 9. Тестирование: unit-тесты сервисов/репозиториев + интеграционные тесты через MockMvc на H2

По правилу проекта (`openspec/config.yaml`, `rules.tasks`) обязательна группа unit-тестов бизнес-логики:

- unit-тесты сервиса привычек с `Clock.fixed(...)`: создание (валидация названия/даты начала/периодичности), редактирование (сохранение отметок), список на произвольную дату (включая дату по умолчанию, прошлую и будущую дату, ошибку ниже самой ранней привычки), история за диапазон (включая `from > to` и отсутствие привычек), отметка/отмена с проверкой диапазона и периодичности, идемпотентность;
- тесты репозиториев на H2 (как `UserRepositoryTest` в gateway) — уникальность отметки, выборка привычек на дату, выборка истории за диапазон, изоляция по `user_id`.

Интеграционные тесты — `@SpringBootTest` + `MockMvc` с H2 и Flyway (тестовый `application.properties` по образцу gateway) — покрывают сценарии спеков, включая `401` без `X-User-Id`, `404` на чужую привычку и `400` на недопустимые даты.

H2 в PostgreSQL-режиме, как в gateway: миграции пишутся в переносимом SQL (без Postgres-only типов), чтобы та же Flyway-миграция применялась и в тестах, и на реальном PostgreSQL.

## Risks / Trade-offs

- **[Risk]** Context-path `/tracker` означает, что сервис нельзя вызвать «по ресурсному» пути (`/habits`) — при прямом обращении к tracker (в обход gateway) нужно помнить про префикс. **Mitigation**: зафиксировать в README/конфигурации сервиса, что tracker доступен через gateway по `/tracker/**`; context-path виден в `application.properties`.
- **[Risk]** Доверие к `X-User-Id` без проверки подписи: при прямом доступе к tracker можно подделать пользователя. **Mitigation**: наследуемое ограничение gateway-этапа; сервис не публикуется наружу, доступ только через gateway (см. design gateway-этапа).
- **[Risk]** Общая база проекта: возможны конфликты имён таблиц и «протечка» связанности между сервисами. **Mitigation**: префикс `tracker_` для всех таблиц и отдельные Flyway-миграции; параметры JDBC берутся из переменных окружения, что позволит вынести tracker на отдельную БД без изменения кода.
- **[Risk]** Редактирование `start_date`/периодичности может сделать ранее сохранённые отметки «не по периодичности» (например, отметка на день, который больше не входит в расписание). **Mitigation**: по решению пользователя отметки не пересчитываются и не удаляются; список на дату и история всегда вычисляются по текущим параметрам привычки. Поведение зафиксировано в спеке (`tracker-habits`, требование о сохранении отметок).
- **[Risk]** Большой диапазон истории (`from`–`to`) даёт объёмный ответ (привычки × дни). **Mitigation**: диапазон задаётся явно и обязателен, нижняя граница ограничена самой ранней привычкой пользователя; пагинация и лимиты вынесены за рамки этапа (см. Non-Goals про аналитику).
- **[Risk]** Будущие даты в списке и истории означают, что ответ описывает расписание, а не только наступившие дни. **Mitigation**: это осознанное решение пользователя; признак `completed` для будущих дней всегда `false`, и это зафиксировано в спеке (`tracker-habits`, требования списка на дату и истории).
- **[Risk]** Часовой пояс сервиса не совпадает с поясом пользователя — «сегодня» у пользователя и в tracker могут расходиться. **Mitigation**: осознанный trade-off первого этапа; пояс вынесен в конфигурацию, переход на пояс пользователя можно добавить отдельным изменением без смены модели данных.
- **[Risk]** Context-path меняет путь и для error-dispatch/служебных эндпоинтов, что может усложнить диагностику. **Mitigation**: тесты на коды ошибок (`400`/`401`/`404`) покрывают фактическое поведение; при необходимости путь ошибок проверяется вручную.

## Migration Plan

Изменение добавляет только новый код и новую схему в `backend/tracker`; существующие данные не переносятся.

1. Добавить в `backend/tracker/pom.xml` зависимости Spring Data JPA, PostgreSQL-драйвер, Flyway (+ `flyway-database-postgresql`), H2 (test scope) по образцу `backend/gateway/pom.xml`.
2. Задать в `application.properties` параметры подключения к общему PostgreSQL через переменные окружения (как в gateway), `ddl-auto=validate`, `flyway.locations=classpath:db/migration`, `server.servlet.context-path=/tracker` и `tracker.time-zone` (по умолчанию `Europe/Moscow`).
3. Применить миграцию `V2__create_tracker_habits_tables.sql` при старте сервиса (Flyway до первого обращения к API).
4. Запустить tracker на порту, на который указывает `gateway.routes[0].target-base-url` (по умолчанию `http://localhost:8081`), и убедиться, что запросы через gateway по `/tracker/**` доходят до сервиса.
5. Секреты/JWT не требуются: сервис доверяет `X-User-Id` от gateway.

Откат: остановить новую версию tracker и (при необходимости) откатить миграцию `V2` — данные привычек созданы этим изменением, других потребителей у таблиц нет.
