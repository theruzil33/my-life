## Context

`client/web` — Vite 8 + React 19 приложение с `react-router-dom` 7, реализованной аутентификацией и общим HTTP-слоем:

- `src/App.jsx` — маршруты `/login`, `/register` (публичные) и `/` под `RequireAuth`;
- `src/pages/HomePage.jsx` — минимальная заглушка: заголовок, email пользователя и кнопка выхода;
- `src/auth/AuthProvider.jsx` — состояние `{ accessToken, email }`, access-токен хранится только в памяти; `logout()`, восстановление сессии через `POST /auth/refresh`;
- `src/api/client.js` — `request(path, { method, body, token, requiresAuth })`: добавляет `Authorization: Bearer`, для изменяющих методов получает и передаёт CSRF-токен, при `401` на защищённом запросе обновляет сессию и повторяет запрос один раз, иначе вызывает обработчик неавторизованности; ошибки приводятся к `ApiError(status, message)` с сообщениями из поля `message` ответа;
- `vite.config.js` — dev-прокси только для префикса `/auth` на `GATEWAY_URL ?? http://localhost:8080`;
- тесты — Vitest + Testing Library в `client/web/test/**` (вне `src/`), API-модули мокаются.

`backend/tracker` уже реализует API привычек, доступный через gateway (изменение backend не входит в рамки):

- gateway сохраняет префикс при проксировании (`target-base-url + requestURI`), поэтому запросы идут на `/tracker/**`, а tracker смонтирован с `server.servlet.context-path=/tracker` и `@RequestMapping("/habits")`;
- эндпоинты: `GET /tracker/habits?date=yyyy-MM-dd`, `POST /tracker/habits`, `GET /tracker/habits/history?from=yyyy-MM-dd&to=yyyy-MM-dd`, `PUT`/`DELETE /tracker/habits/{id}/completions/{date}`;
- форматы JSON: привычка — `{ id, name, startDate, frequency, weekdays }`; привычка на дату — то же плюс `date`, `completed`; история — то же плюс `days: [{ date, completed }]`; `frequency` — `DAILY` или `SPECIFIC_WEEKDAYS`, `weekdays` — имена дней недели (`MONDAY`…`SUNDAY`);
- трекер валидирует данные: пустое название, дата начала в прошлом, отсутствие периодичности, диапазон `from` позже `to`, `from` (или `date`) раньше самой ранней даты начала привычек пользователя → `400` c `{ message }`; отметка на будущую дату, дату раньше начала привычки или день не по периодичности → `400`;
- идентификатор пользователя трекер получает из заголовка `X-User-Id`, который проставляет gateway; клиенту об этом знать не нужно.

Мотивация изменения — в `proposal.md`, требования к поведению — в `specs/web-app-hub/spec.md` и `specs/web-tracker/spec.md`. Здесь фиксируются только технические решения.

## Goals / Non-Goals

**Goals:**

- Определить структуру маршрутизации хаба и страницы трекера и модель данных каталога приложений.
- Зафиксировать модуль API трекера и способ передачи access-токена и CSRF-токена через существующий `request()`.
- Зафиксировать работу с датами (сегодня, границы диапазона, недоступность будущих дат) так, чтобы поведение было тестируемым.
- Зафиксировать поток данных вкладок «Привычки» и «Статистика», включая состояния загрузки, пустоты и ошибок.
- Зафиксировать построение матрицы статистики и правила выбора диапазона.
- Зафиксировать модальное окно создания привычки, клиентскую валидацию и поведение при ошибках.
- Определить состав тестов по существующему соглашению (`test/**`, моки API).

**Non-Goals:**

- Изменения в `backend/tracker` и `backend/gateway`: используется существующий контракт и маршрутизация.
- Изменение и удаление привычки в интерфейсе (`PUT /tracker/habits/{id}` и удаление не используются), хотя API их поддерживает.
- Аналитика поверх истории: стрики, проценты, агрегированные графики, сортировки и фильтры. Статистика — только матрица «привычки × дни».
- Дизайн-система, тема, адаптивная вёрстка под мобильные, анимации.
- Выбор часового пояса пользователем и синхронизация «сегодня» клиента с часовым поясом сервиса.
- Пагинация и виртуализация больших диапазонов; отметка и просмотр будущих дней.
- E2E-тесты в браузере (Playwright) и изменения CI.

## Decisions

### 1. Каталог приложений задаётся данными, хаб строит из него карточки

Добавляется модуль `src/apps/apps.js` с массивом приложений: `{ id, title, path, enabled }`. Сейчас в нём карточка `{ id: 'tracker', title: 'Трекер', path: '/tracker', enabled: true }` и неактивные карточки-заглушки (`enabled: false`, без `path`). `HomePage` сохраняет email и кнопку выхода, а по центру рендерит сетку карточек: активные — ссылки/кнопки с переходом на `path`, неактивные — неинтерактивные карточки с признаком недоступности (`aria-disabled`).

Альтернатива — захардкодить карточки прямо в `HomePage` — отклонена: появление второго приложения потребовало бы правок разметки, тогда как каталог отделяет «список приложений» от «отрисовки сетки». Альтернатива — генерировать каталог с сервера — отклонена: backend не меняется, а перечень приложений статичен и известен на этапе сборки.

### 2. Маршруты: `/` — хаб, `/tracker` — страница трекера, оба под `RequireAuth`

В `src/App.jsx` добавляется маршрут `/tracker` с тем же `RequireAuth`, что и `/`. `HomePage` остаётся компонентом хаба, добавляется `src/pages/TrackerPage.jsx`. Возврат на хаб — обычная навигация на `/` (ссылка/кнопка).

Вкладки внутри трекера — локальное состояние `TrackerPage` (`useState`), а не вложенные маршруты: по умолчанию «Привычки», переключение сохраняет выбранную дату/диапазон между вкладками. Альтернатива — маршруты `/tracker/habits` и `/tracker/statistics` — отклонена: спека не требует deep-link на вкладку, а локальное состояние проще и сохраняет выбор пользователя при переключении; переход на маршруты можно сделать позже без смены API и данных.

### 3. Модуль API трекера использует общий `request()` и токен из `AuthProvider`

Добавляется `src/api/trackerApi.js` с функциями, принимающими `token` первым аргументом:

- `listOnDate(token, date)` → `GET /tracker/habits?date=...`;
- `create(token, { name, startDate, frequency, weekdays })` → `POST /tracker/habits`;
- `history(token, from, to)` → `GET /tracker/habits/history?from=...&to=...`;
- `markCompleted(token, habitId, date)` → `PUT /tracker/habits/{id}/completions/{date}`;
- `unmarkCompleted(token, habitId, date)` → `DELETE /tracker/habits/{id}/completions/{date}`.

Все вызовы идут через `request(..., { requiresAuth: true, token })`, поэтому заголовок `Authorization: Bearer`, CSRF-заголовок для `POST`/`PUT`/`DELETE` и обработка `401` с обновлением сессии и повтором запроса достаются из существующего HTTP-слоя без дублирования. Компоненты получают токен из `useAuth()` и передают его в вызовы.

Альтернатива — отдельный `fetch`-враппер для трекера — отклонена: пришлось бы повторять CSRF, refresh-on-401 и приведение ошибок. Альтернатива — читать токен из модуля/контекста внутри API-слоя — отклонена: ломает существующий дизайн, где токен передаётся аргументом (HTTP-слой тестируется изолированно).

### 4. Даты обрабатываются в локальной зоне браузера через отдельный модуль

Добавляется `src/tracker/dates.js` с чистыми функциями: `todayIso()` (сегодняшняя дата из локальных компонент `Date`, без `toISOString()`, который использует UTC и может дать соседний день), `firstDayOfMonthIso()`, `addDays`, `eachIsoDate(from, to)`, `isAfter(date, other)`, `formatDayLabel(date)`.

Даты в API и в элементах `input type="date"` — ISO `yyyy-MM-dd`. Ограничение «не позже сегодня» реализуется атрибутом `max={todayIso()}` у полей даты и дополнительной проверкой значения в коде (нативные ограничения зависят от браузера). Отдельный модуль делает арифметику диапазонов и «сегодня» тестируемыми без рендера компонентов.

Альтернатива — вычислять даты внутри компонентов — отклонена: логика вида «первый день месяца», «все дни диапазона», «не в будущем» повторяется в трёх местах (список, статистика, модалка) и трудно покрывается тестами. Альтернатива — брать «сегодня» с сервера — отклонена: API не отдаёт серверную дату, а backend не меняется.

### 5. Вкладка «Привычки»: загрузка по дате, отметка без оптимистичного обновления

`HabitsTab` хранит выбранную дату, список привычек, состояния загрузки и ошибки. Запрос `listOnDate` выполняется при монтировании и при каждой смене даты; список очищается на время загрузки, чтобы не показывать данные предыдущей даты. Пустой ответ — пустое состояние, ошибка — сообщение об ошибке без списка.

Отметка выполнения: состояние ожидания ведётся по `habitId` (множество id), поэтому блокируется только чекбокс изменяемой привычки. Запрос отправляется после переключения чекбокса, но UI обновляется только по успешному ответу трекера (`completed` из ответа); при ошибке показывается сообщение и восстанавливается предыдущее состояние. Оптимистичное обновление с откатом не используется: спека требует состояния «как до запроса» при ошибке, а лишний код отката не даёт выигрыша на локальной сети.

Альтернатива — перезагружать весь список после каждой отметки — отклонена: лишний запрос и мигание списка. Альтернатива — оптимистичное обновление — отклонена как источник рассинхронизации с сервером при ошибках.

### 6. Модальное окно создания привычки: собственная форма, валидация из отдельного модуля

Добавляется `src/tracker/validation.js` с чистой функцией валидации формы привычки, повторяющей правила трекера: имя после `trim` непустое; дата начала не раньше `todayIso()`; `frequency` — `DAILY` или `SPECIFIC_WEEKDAYS`, при этом для `SPECIFIC_WEEKDAYS` выбран хотя бы один день недели. Константы периодичности и дней недели (ISO 1–7 с русскими подписями) лежат в `src/tracker/habitOptions.js`.

Компонент `src/tracker/HabitFormModal.jsx` — кастомная модалка (не `<dialog>` и не сторонняя библиотека): оверлей, `role="dialog"`, `aria-modal`, заголовок, форма, кнопки «Создать» и «Отмена». Оверлей скрывается, форма блокируется на время запроса. Закрытие без сохранения — «Отмена», `Escape` или клик по оверлею. Дни недели показываются только для `SPECIFIC_WEEKDAYS`; для `DAILY` в запрос уходит пустой список дней (в соответствии с контрактом API поле можно не передавать). Значения по умолчанию: пустое название, дата начала — сегодня, периодичность `DAILY`.

При успехе модалка закрывается и `HabitsTab` повторно запрашивает список текущей даты (созданная привычка с будущей датой начала в списке на сегодня не появится — это ожидаемое поведение). При ошибке `ApiError` (в том числе `400` с сообщением трекера) модалка остаётся открытой с введёнными значениями и показывает сообщение.

Альтернатива — нативный `<dialog>` — отклонена: поведение и стилизация различаются между браузерами, а требование явно просит кастомную модалку. Альтернатива — библиотека компонентов — отклонена: не оправдана для одной формы.

### 7. Вкладка «Статистика»: матрица из ответа истории

`StatisticsTab` хранит применённый диапазон, данные истории, состояния загрузки и ошибки. Запрос `history(token, from, to)` выполняется при монтировании вкладки (или при первом её открытии) и при применении нового диапазона. Матрица строится из ответа:

- столбцы — все даты `eachIsoDate(from, to)`;
- строки — привычки из ответа (`id`, `name`);
- для каждой привычки из `days` строятся множество запланированных дат и множество выполненных дат;
- квадрат дня: выполнен и запланирован → закрашен; запланирован и не выполнен → контур/незакрашенный; не запланирован (даты нет в `days`) → приглушённый пустой квадрат.

Дни вне периодичности отдельно не запрашиваются: трекер не перечисляет их в `days`, поэтому «приглушённый» статус выводится из отсутствия даты в ответе. Контейнер матрицы прокручивается по горизонтали при широком диапазоне; имена привычек и подписи дней видимы, квадраты имеют текстовые `aria-label`/`title` с датой и статусом, чтобы их можно было проверять в тестах и читать скринридером. Пустой ответ — пустое состояние.

Альтернатива — строить матрицу по календарю месяца с агрегатом по дням — отклонена пользователем: нужны строки-привычки и столбцы-дни. Альтернатива — достраивать не запланированные дни клиентом по `frequency`/`weekdays` — отклонена: ответ уже однозначно определяет запланированные дни, а дублирование логики расписания на клиенте рискует разойтись с трекером.

### 8. Диапазон статистики: по умолчанию текущий месяц, применение по кнопке

Начальный диапазон — с первого числа текущего месяца по сегодня (`firstDayOfMonthIso()` … `todayIso()`). Поля начала и конца ограничены `max={todayIso()}`. Новый диапазон применяется по кнопке «Применить», а не на каждое изменение поля, чтобы промежуточные значения не порождали запросы. Если начало позже конца, диапазон не применяется и показывается сообщение; запрос не отправляется. Если трекер отвечает `400` (например, начало раньше самой ранней привычки пользователя), показывается сообщение трекера, а ранее отображённый диапазон и матрица сохраняются.

Клиент не знает самую раннюю дату начала привычек (API её не отдаёт), поэтому «подтягивать» нижнюю границу нечем — ошибка сервера показывается пользователю. Альтернатива — вычислять минимум из ответа истории — отклонена: ответ приходит только для валидного диапазона, то есть неприменим для невалидного.

### 9. Ошибки и состояния: сообщения `ApiError`, отсутствие устаревших данных

Для каждого запроса (список, история, создание, отметка) есть локальное состояние ошибки; текст берётся из `ApiError.message` (сообщения `client.js`, включая `message` трекера для `400`). При неудачной загрузке список/матрица не показываются — вместо них сообщение об ошибке и, где уместно, повторная попытка (повторный запрос при смене даты/диапазона или нажатии «Обновить»). Глобальная обработка `401` (обновление сессии и повтор, иначе выход и переход на вход) остаётся в `request()` и не дублируется в компонентах трекера.

### 10. Dev-прокси Vite расширяется префиксом `/tracker`

В `vite.config.js` добавляется прокси `/tracker` на `GATEWAY_URL ?? http://localhost:8080` рядом с `/auth`. Базовый URL API (`VITE_API_BASE_URL`) не меняется, вызовы остаются относительными (`/tracker/...`), CSRF-cookie и cookie refresh-токена ходят на тот же origin.

### 11. Тесты: Vitest + Testing Library, моки API, тесты вне `src/`

По существующему соглашению добавляются тесты в `client/web/test/**`:

## Risks / Trade-offs

- **[Risk]** «Сегодня» на клиенте (локальная зона браузера) может не совпадать с «сегодня» трекера (`tracker.time-zone`, по умолчанию `Europe/Moscow`); в пограничные часы список/отметка могут вести себя неожиданно. **Mitigation**: клиент единообразно использует локальную дату, ограничение `max` и проверки построены на ней; расхождение — известный trade-off, устранимое отдельным изменением (например, эндпоинт «сегодня» или пояс пользователя).
- **[Risk]** `input type="date"` и его `min`/`max` по-разному ведут себя в браузерах, поэтому будущую дату можно ввести вручную. **Mitigation**: помимо `max`, значение проверяется в коде перед запросом (даты и диапазон), что покрыто unit-тестами.
- **[Risk]** Диапазон статистики раньше самой ранней привычки даёт `400`, и пользователь видит ошибку вместо скорректированного диапазона. **Mitigation**: понятное сообщение из ответа трекера, сохранение предыдущей матрицы; при необходимости API можно расширить позже, это не меняет спеку.
- **[Risk]** Клиентская валидация дублирует правила трекера и может разойтись с ними. **Mitigation**: единый модуль `validation.js`, тесты на границы, а сообщения `400` трекера всё равно показываются пользователю.
- **[Risk]** Большой диапазон (много привычек × много дней) даёт много DOM-узлов. **Mitigation**: горизонтальная прокрутка, диапазон по умолчанию ограничен текущим месяцем; лимиты и виртуализация вынесены в Non-Goals.
- **[Risk]** Трекер недоступен без запущенных gateway и tracker, а dev-прокси работает только в режиме разработки. **Mitigation**: ошибки сети отображаются понятными сообщениями, тесты полностью мокают API; порядок запуска фиксируется в задачах.
- **[Risk]** Карточки-заглушки могут выглядеть кликабельными и создавать «мёртвые» клики. **Mitigation**: неактивные карточки не являются ссылками/кнопками, помечены визуально и через `aria-disabled`.
- **[Risk]** Вкладки как локальное состояние теряют активную вкладку при перезагрузке и не имеют deep-link. **Mitigation**: спека этого не требует; выделение вкладок в маршруты возможно позже без изменения API.

## Migration Plan

Изменение затрагивает только фронтенд `client/web`; данные не переносятся, миграций БД и изменений backend нет.

1. Убедиться, что запущены gateway (порт 8080) и tracker (порт 8081, context-path `/tracker`); маршрут `/tracker/**` уже настроен в `gateway.routes[0]`.
2. В `client/web` выполнить `npm install` (новых зависимостей не ожидается) и `npm run dev`; dev-сервер проксирует `/auth` и `/tracker` на gateway.
3. Проверить сценарии: карточки на главной, переход в трекер, список на сегодня, выбор прошлой даты, отметка/снятие, создание привычки (ежедневной и по дням), ошибки валидации, статистика за текущий месяц и за выбранный диапазон.
4. Прогнать `npm run lint`, `npm run test:run`, `npm run build`.

Откат: изменение локализовано во фронтенде — достаточно откатить коммит (вернуть прежний `HomePage.jsx`/`App.jsx` и удалить добавленные модули); backend и данные не затрагиваются. Флагов функций нет.
