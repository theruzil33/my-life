## MODIFIED Requirements

### Requirement: Вход в систему и сохранение access-токена

Веб-клиент SHALL предоставлять форму входа с полями email и пароля, которая отправляет данные в эндпоинт входа gateway. При успешном входе веб-клиент SHALL сохранять полученный JWT access-токен только в памяти приложения (без записи в `localStorage` или `sessionStorage`), получать от gateway установленную httpOnly cookie с refresh-токеном и переводить пользователя в аутентифицированное состояние с email вошедшего пользователя.

#### Scenario: Успешный вход

- **WHEN** пользователь отправляет форму входа с корректными email и паролем зарегистрированного пользователя
- **THEN** веб-клиент сохраняет access-токен в памяти, показывает аутентифицированное состояние с email вошедшего пользователя и возможностью выхода, а браузер сохраняет установленную gateway httpOnly cookie refresh-токена

#### Scenario: Токены не записываются в доступное JavaScript хранилище

- **WHEN** пользователь вошёл в систему
- **THEN** ни access-токен, ни refresh-токен не присутствуют в `localStorage` или `sessionStorage`, и refresh-токен недоступен JavaScript

#### Scenario: Отклонение входа с неверными учётными данными

- **WHEN** gateway отвечает на запрос входа ошибкой аутентификации
- **THEN** веб-клиент показывает сообщение о неверном email или пароле, не раскрывая, какой именно из параметров неверен, и остаётся в неаутентифицированном состоянии

#### Scenario: Вход недоступен при незаполненных полях

- **WHEN** пользователь пытается отправить форму входа с пустым email или пустым паролем
- **THEN** веб-клиент не отправляет запрос в gateway и показывает, какие поля необходимо заполнить

### Requirement: Сохранение сессии между перезагрузками страницы

Веб-клиент SHALL восстанавливать аутентифицированное состояние после перезагрузки страницы, обращаясь к эндпоинту обновления сессии gateway с httpOnly cookie refresh-токена, и MUST NOT восстанавливать сессию из локального хранилища. При успешном обновлении веб-клиент получает новый access-токен и email пользователя; при отсутствии или недействительности refresh-токена веб-клиент остаётся в неаутентифицированном состоянии.

#### Scenario: Сессия сохраняется после перезагрузки

- **WHEN** пользователь успешно вошёл в систему и перезагружает страницу приложения, имея действующую httpOnly cookie refresh-токена
- **THEN** веб-клиент восстанавливает аутентифицированное состояние без повторного ввода учётных данных

#### Scenario: Отсутствие сохранённого токена

- **WHEN** пользователь открывает приложение, ни разу не входивший в систему или ранее вышедший из неё
- **THEN** веб-клиент находится в неаутентифицированном состоянии и показывает форму входа, не выполняя попыток восстановления из локального хранилища

#### Scenario: Недействительный refresh-токен при восстановлении

- **WHEN** при открытии приложения сохранённый refresh-токен истёк или отозван
- **THEN** веб-клиент остаётся в неаутентифицированном состоянии и показывает форму входа, не показывая ошибку сервера

### Requirement: Выход из системы

Веб-клиент SHALL предоставлять пользователю действие выхода из системы, которое вызывает эндпоинт выхода gateway (отзыв refresh-токена на сервере), удаляет access-токен из памяти и переводит приложение в неаутентифицированное состояние. Веб-клиент MUST NOT полагаться только на удаление локальных данных. Если вызов эндпоинта выхода не удался, веб-клиент SHALL всё равно завершить локальный выход.

#### Scenario: Выход из аутентифицированного состояния

- **WHEN** аутентифицированный пользователь выполняет выход
- **THEN** веб-клиент вызывает эндпоинт выхода gateway, удаляет access-токен из памяти и показывает форму входа

#### Scenario: Выход при недоступности gateway

- **WHEN** пользователь выполняет выход, а gateway недоступен или отвечает ошибкой
- **THEN** веб-клиент всё равно удаляет access-токен из памяти и переводит приложение в неаутентифицированное состояние

#### Scenario: Повторное открытие приложения после выхода

- **WHEN** пользователь выполнил выход и перезагружает страницу приложения
- **THEN** веб-клиент остаётся в неаутентифицированном состоянии и не предъявляет refresh-токен для восстановления сессии

### Requirement: Передача access-токена в защищённых запросах

Веб-клиент SHALL передавать access-токен из памяти в заголовке авторизации защищённых запросов к gateway в формате `Bearer`. Если access-токен отсутствует, веб-клиент MUST NOT добавлять заголовок авторизации и MUST NOT отправлять защищённый запрос.

#### Scenario: Заголовок авторизации добавляется при наличии токена

- **WHEN** аутентифицированный пользователь инициирует защищённый запрос к gateway
- **THEN** веб-клиент отправляет запрос с заголовком авторизации, содержащим access-токен из памяти в формате `Bearer`

#### Scenario: Заголовок авторизации не добавляется без токена

- **WHEN** неаутентифицированный пользователь инициирует защищённый запрос к gateway
- **THEN** веб-клиент не отправляет запрос

### Requirement: Защита аутентифицированных страниц

Веб-клиент SHALL разделять страницы на публичные (вход и регистрация) и аутентифицированные. Сессия считается аутентифицированной при наличии access-токена в памяти или действующего refresh-токена, который был успешно использован для восстановления сессии. При попытке открыть аутентифицированную страницу в неаутентифицированном состоянии веб-клиент MUST перенаправлять пользователя на страницу входа.

#### Scenario: Неаутентифицированный доступ к защищённой странице

- **WHEN** пользователь без access-токена и без действующего refresh-токена открывает аутентифицированную страницу
- **THEN** веб-клиент перенаправляет пользователя на страницу входа

#### Scenario: Переход между входом и регистрацией

- **WHEN** пользователь находится на странице входа или регистрации
- **THEN** веб-клиент предоставляет переход к другой из этих страниц

#### Scenario: Аутентифицированный доступ к защищённой странице

- **WHEN** пользователь с access-токеном в памяти или успешно восстановленной сессией открывает аутентифицированную страницу
- **THEN** веб-клиент показывает эту страницу без перенаправления на вход

#### Scenario: Истёкший или недействительный access-токен

- **WHEN** gateway отвечает ошибкой аутентификации на защищённый запрос, так как access-токен истёк или недействителен
- **THEN** веб-клиент пытается обновить сессию через эндпоинт обновления и только при неудаче удаляет access-токен и перенаправляет пользователя на страницу входа

## ADDED Requirements

### Requirement: Передача cookie refresh-токена в запросах аутентификации

Веб-клиент SHALL отправлять запросы к эндпоинтам аутентификации gateway с учётом cookie, чтобы httpOnly cookie refresh-токена передавалась на gateway при обновлении сессии и выходе и сохранялась из ответа на вход.

#### Scenario: Refresh-запрос передаёт refresh cookie

- **WHEN** веб-клиент вызывает эндпоинт обновления сессии
- **THEN** запрос отправляется с передачей cookie, и gateway получает httpOnly cookie refresh-токена

#### Scenario: Запрос выхода передаёт refresh cookie

- **WHEN** веб-клиент вызывает эндпоинт выхода
- **THEN** запрос отправляется с передачей cookie, и gateway получает httpOnly cookie refresh-токена

### Requirement: Передача CSRF-токена в изменяющих запросах

Веб-клиент SHALL получать CSRF-токен от gateway и передавать его в согласованном заголовке при изменяющих запросах (POST, PUT, PATCH, DELETE), включая регистрацию, вход, обновление сессии и выход. Веб-клиент MUST NOT отправлять изменяющий запрос без CSRF-токена.

#### Scenario: CSRF-токен добавляется к изменяющему запросу

- **WHEN** веб-клиент отправляет изменяющий запрос к gateway (регистрация, вход, обновление или выход)
- **THEN** запрос содержит заголовок с полученным CSRF-токеном и cookie с CSRF-токеном

#### Scenario: CSRF-токен запрашивается до первого изменяющего запроса

- **WHEN** веб-клиент ещё не получал CSRF-токен и пользователь инициирует изменяющий запрос
- **THEN** веб-клиент сначала получает CSRF-токен у gateway, а затем отправляет изменяющий запрос с этим токеном

#### Scenario: Отклонение изменяющего запроса по CSRF

- **WHEN** gateway отвечает на изменяющий запрос ошибкой CSRF-защиты
- **THEN** веб-клиент повторно получает CSRF-токен и показывает пользователю понятное сообщение, не переводя его в аутентифицированное состояние

### Requirement: Автоматическое обновление сессии при истёкшем access-токене

Веб-клиент SHALL автоматически обновлять сессию при получении ошибки аутентификации от gateway из-за истёкшего access-токена: обновить сессию через эндпоинт обновления и, при успехе, повторить исходный запрос с новым access-токеном. При неудаче обновления веб-клиент MUST очистить состояние сессии и перенаправить пользователя на страницу входа. Одновременные запросы, получившие такую ошибку, MUST использовать одно обновление сессии, не выполняя его многократно.

#### Scenario: Успешное обновление и повтор запроса

- **WHEN** защищённый запрос отклонён gateway из-за истёкшего access-токена, а refresh-токен действителен
- **THEN** веб-клиент обновляет сессию, повторяет исходный запрос с новым access-токеном и возвращает пользователю результат повторного запроса без его участия

#### Scenario: Неудачное обновление завершает сессию

- **WHEN** защищённый запрос отклонён из-за истёкшего access-токена, а обновить сессию не удалось
- **THEN** веб-клиент очищает состояние сессии и перенаправляет пользователя на страницу входа

#### Scenario: Параллельные запросы используют одно обновление

- **WHEN** несколько защищённых запросов одновременно получают ошибку аутентификации из-за истёкшего access-токена
- **THEN** веб-клиент выполняет одно обновление сессии и повторяет исходные запросы с полученным access-токеном
