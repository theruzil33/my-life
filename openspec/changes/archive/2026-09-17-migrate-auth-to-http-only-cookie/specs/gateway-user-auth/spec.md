## MODIFIED Requirements

### Requirement: Вход в систему и выдача JWT access-токена

Gateway SHALL предоставлять эндпоинт входа, который проверяет пару email/пароль и при успехе выдаёт подписанный JWT access-токен с ограниченным сроком действия и refresh-токен. Access-токен SHALL возвращаться в теле ответа вместе с email пользователя. Refresh-токен MUST передаваться клиенту только в httpOnly cookie и MUST NOT присутствовать в теле ответа. Cookie refresh-токена MUST быть недоступна JavaScript (HttpOnly) и MUST ограничивать область отправки.

#### Scenario: Успешный вход

- **WHEN** клиент отправляет корректные email и пароль зарегистрированного пользователя
- **THEN** gateway возвращает access-токен со сроком действия и email пользователя, устанавливает httpOnly cookie с refresh-токеном и не возвращает пароль, его хеш или refresh-токен в теле

#### Scenario: Cookie refresh-токена недоступна JavaScript

- **WHEN** gateway отвечает на успешный вход
- **THEN** устанавливаемая cookie refresh-токена помечена флагом `HttpOnly` и не может быть прочитана из JavaScript

#### Scenario: Отклонение входа с неверным паролем

- **WHEN** клиент отправляет существующий email и неверный пароль
- **THEN** gateway отклоняет запрос с ошибкой аутентификации, не раскрывая, какой из параметров неверен, и не устанавливает cookie refresh-токена

#### Scenario: Отклонение входа для незарегистрированного email

- **WHEN** клиент отправляет email, для которого пользователь не зарегистрирован
- **THEN** gateway отклоняет запрос с тем же ответом, что и при неверном пароле, и не устанавливает cookie refresh-токена

### Requirement: Публичные эндпоинты без проверки токена

Gateway SHALL позволять обращаться к эндпоинтам регистрации, входа, обновления сессии и выхода без JWT access-токена, сохраняя проверку токена для остальных маршрутов. Эндпоинты обновления сессии и выхода SHALL при этом требовать действующий refresh-токен в cookie (для выхода допускается отсутствие токена) и SHALL быть защищены от CSRF.

#### Scenario: Обращение к эндпоинту регистрации без токена

- **WHEN** клиент вызывает эндпоинт регистрации без заголовка авторизации
- **THEN** gateway обрабатывает запрос, не требуя JWT access-токен

#### Scenario: Обращение к эндпоинту входа без токена

- **WHEN** клиент вызывает эндпоинт входа без заголовка авторизации
- **THEN** gateway обрабатывает запрос, не требуя JWT access-токен

#### Scenario: Обращение к эндпоинту обновления без access-токена

- **WHEN** клиент вызывает эндпоинт обновления сессии с действительной refresh cookie, но без заголовка авторизации
- **THEN** gateway обрабатывает запрос, не требуя JWT access-токен

#### Scenario: Обращение к эндпоинту выхода без access-токена

- **WHEN** клиент вызывает эндпоинт выхода без заголовка авторизации
- **THEN** gateway обрабатывает запрос, не требуя JWT access-токен

## ADDED Requirements

### Requirement: Обновление сессии по refresh-токену с ротацией

Gateway SHALL предоставлять эндпоинт обновления сессии, который принимает refresh-токен из httpOnly cookie, проверяет его действительность и неотозванность, отзывает использованный refresh-токен и выдаёт новую пару: новый access-токен в теле ответа и новый refresh-токен в cookie. Отсутствующий, неизвестный, истёкший или уже отозванный refresh-токен MUST приводить к ошибке аутентификации без выдачи новых токенов.

#### Scenario: Успешное обновление сессии

- **WHEN** клиент вызывает эндпоинт обновления с действительной refresh cookie
- **THEN** gateway отзывает использованный refresh-токен, выдаёт новый access-токен в теле ответа и устанавливает новую httpOnly cookie с новым refresh-токеном

#### Scenario: Отклонение при отсутствии refresh cookie

- **WHEN** клиент вызывает эндпоинт обновления без cookie refresh-токена
- **THEN** gateway отвечает ошибкой аутентификации и не выдаёт access-токен

#### Scenario: Отклонение при неизвестном refresh-токене

- **WHEN** клиент вызывает эндпоинт обновления с refresh-токеном, который не был выдан gateway
- **THEN** gateway отвечает ошибкой аутентификации и не выдаёт access-токен

#### Scenario: Отклонение при истёкшем refresh-токене

- **WHEN** клиент вызывает эндпоинт обновления с refresh-токеном, срок действия которого истёк
- **THEN** gateway отвечает ошибкой аутентификации и не выдаёт access-токен

#### Scenario: Повторное использование отозванного refresh-токена

- **WHEN** клиент повторно использует refresh-токен, который уже был обменян или отозван
- **THEN** gateway отвечает ошибкой аутентификации и не выдаёт access-токен

### Requirement: Выход из системы с отзывом refresh-токена

Gateway SHALL предоставлять эндпоинт выхода, который отзывает refresh-токен из cookie и удаляет cookie. После успешного выхода отозванный refresh-токен MUST NOT позволять получить новый access-токен. Выход SHALL отзывать только сессию, соответствующую предъявленному refresh-токену, не затрагивая другие активные сессии пользователя.

#### Scenario: Успешный выход

- **WHEN** аутентифицированный клиент вызывает эндпоинт выхода с действительной refresh cookie
- **THEN** gateway отзывает соответствующий refresh-токен, удаляет cookie и возвращает успешный ответ

#### Scenario: Отозванный refresh-токен не работает после выхода

- **WHEN** после успешного выхода клиент пытается обновить сессию с тем же refresh-токеном
- **THEN** gateway отвечает ошибкой аутентификации и не выдаёт access-токен

#### Scenario: Выход без refresh cookie

- **WHEN** клиент вызывает эндпоинт выхода без cookie refresh-токена
- **THEN** gateway завершает запрос без ошибки сервера и без отзыва чужих сессий

#### Scenario: Выход не затрагивает другие сессии

- **WHEN** у пользователя есть две активные сессии и он выполняет выход в одной из них
- **THEN** refresh-токен второй сессии остаётся действительным

### Requirement: Защита изменяющих запросов от CSRF

Gateway SHALL защищать изменяющие состояние запросы (методы, отличные от безопасных: POST, PUT, PATCH, DELETE) от CSRF с помощью проверки CSRF-токена Spring Security. CSRF-токен SHALL передаваться клиенту в cookie, доступной JavaScript, а изменяющий запрос MUST содержать этот токен в согласованном заголовке. Запрос с отсутствующим или неверным CSRF-токеном MUST быть отклонён без выполнения действия. Gateway SHALL предоставлять публичный эндпоинт получения CSRF-токена, доступный до аутентификации.

#### Scenario: Получение CSRF-токена до аутентификации

- **WHEN** неаутентифицированный клиент обращается к эндпоинту получения CSRF-токена
- **THEN** gateway выдаёт доступную JavaScript cookie с CSRF-токеном и не требует аутентификации

#### Scenario: Изменяющий запрос без CSRF-токена отклоняется

- **WHEN** клиент отправляет изменяющий запрос без заголовка с CSRF-токеном
- **THEN** gateway отклоняет запрос и не выполняет действие (не выдаёт токены, не меняет сессию)

#### Scenario: Изменяющий запрос с неверным CSRF-токеном отклоняется

- **WHEN** клиент отправляет изменяющий запрос с CSRF-токеном, не соответствующим выданному
- **THEN** gateway отклоняет запрос и не выполняет действие

#### Scenario: Изменяющий запрос с валидным CSRF-токеном выполняется

- **WHEN** клиент отправляет изменяющий запрос с корректным CSRF-токеном в заголовке и cookie
- **THEN** gateway обрабатывает запрос как обычно

### Requirement: Хранение refresh-токенов и срок их действия

Gateway SHALL хранить refresh-токены в БД в виде, не позволяющем восстановить исходное значение токена из хранилища, с привязкой к пользователю и сроком действия, задаваемым конфигурацией.

#### Scenario: Refresh-токен имеет ограниченный срок действия

- **WHEN** истёк срок действия refresh-токена, заданный конфигурацией gateway
- **THEN** такой refresh-токен не позволяет обновить сессию

#### Scenario: Выданный refresh-токен не хранится в открытом виде

- **WHEN** refresh-токен выдан пользователю
- **THEN** в хранилище gateway отсутствует исходное значение refresh-токена
