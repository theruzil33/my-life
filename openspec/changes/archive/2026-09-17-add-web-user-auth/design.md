## Context

`client/web` — это стандартный Vite 8 + React 19 каркас (`npm create vite`), в котором есть только демонстрационный `src/App.jsx` (Vite-заглушка), `src/main.jsx`, стили и `eslint.config.js`. Маршрутизации, HTTP-клиента, состояния аутентификации и тестовой инфраструктуры нет; тестовый скрипт в `client/web/package.json` отсутствует, lint запускается через `npm run lint`.

Gateway (`backend/gateway`, порт по умолчанию 8080) уже реализует нужные эндпоинты (см. `openspec/specs/gateway-user-auth/spec.md`):

- `POST /auth/register`, тело `{ email, password }` → `201` и тело `{ id, email }`; ошибки `409` (email занят) и `400` (валидация) в формате `{ message }`.
- `POST /auth/login`, тело `{ email, password }` → `200` и тело `{ accessToken, tokenType, expiresIn }`; ошибка `401` в формате `{ message }`.
- Зарезервированные за gateway пути: `/auth/**`; JWT — HS256, claim `sub` содержит id пользователя, TTL по умолчанию 1 час; refresh-токена нет.
- CORS на gateway не настроен, `backend/**` в этом изменении не модифицируется.

Мотивация изменения — в `proposal.md`; требования к поведению — в `specs/web-user-auth/spec.md`. Здесь фиксируются только технические решения.

## Goals / Non-Goals

**Goals:**
- Определить структуру маршрутизации и защиты аутентифицированных страниц веб-клиента.
- Зафиксировать способ хранения access-токена и модель состояния аутентификации.
- Зафиксировать HTTP-слой и способ доступа к gateway из dev-окружения без изменений бэкенда.
- Зафиксировать отображение ошибок gateway и клиентскую валидацию, согласованную с правилами gateway.
- Определить состав тестовой инфраструктуры и границы тестов.
- Разместить тесты в отдельной папке `client/web/test/**`, чтобы не смешивать их с исходным кодом в `src/**`.

**Non-Goals:**
- Изменения в `backend/gateway` (CORS, новые эндпоинты, refresh-токены) — вне рамок; используется существующий контракт.
- UI для доменных данных (tracker и далее), глобальный layout/дизайн-система; защищённая страница — минимальная заглушка с приветствием и выходом.
- Восстановление пароля, подтверждение email, «запомнить меня», хранение токена в httpOnly cookie.
- SSR, TypeScript, state-менеджеры (Redux/Zustand), интернационализация.

## Decisions

### 1. Маршрутизация: react-router-dom

Добавляется `react-router-dom`. Маршруты: `/login` и `/register` — публичные, `/` — аутентифицированный. Защита реализуется компонентом-обёрткой (`RequireAuth`), который при отсутствии access-токена делает `<Navigate to="/login" replace />`. При успешном входе выполняется переход на `/`.

Почему не ручное переключение представлений через состояние: требование «Защита аутентифицированных страниц» и сценарий «Переход между входом и регистрацией» подразумевают адресуемые экраны; с роутером появление новых защищённых страниц (tracker UI) не потребует переписывания навигации. Альтернатива «одна страница с переключением форм» дешевле (нет зависимости), но плохо масштабируется и не даёт deep-link на форму. Пользователь подтвердил выбор роутера.

### 2. Состояние аутентификации: React Context + localStorage

Один `AuthProvider` (контекст + хук `useAuth()`) хранит состояние `{ accessToken, email }` и предоставляет `login(credentials)`, `register(credentials)`, `logout()`. Состояние инициализируется из `localStorage` при старте приложения и записывается туда при входе/выходе, что закрывает сценарий «Сохранение сессии между перезагрузками страницы».

`email` хранится рядом с токеном, потому что ответ логина (`TokenResponse`) не содержит данных пользователя, а JWT в `sub` несёт только числовой id; email, введённый при успешном входе, — единственный понятный пользователю идентификатор. Альтернатива — декодировать payload JWT и показывать `sub` — отклонена как менее информативная для пользователя; полноценный профиль потребовал бы нового эндпоинта gateway (вне рамок).

Альтернативы управления состоянием — пропсы, Redux, Zustand — отклонены: состояние нужно в разных точках дерева (защищённый маршрут, страницы, заголовок), а объём состояния минимален; контекста достаточно без новых зависимостей.

### 3. HTTP-слой: нативный fetch в небольшом модуле

Запросы выполняются нативным `fetch` в модуле `src/api/` (общий `request()` + `authApi.register()`/`authApi.login()`), без axios. Общий помощник:

- формирует URL относительно базового адреса и JSON-заголовки;
- разбирает тело ответа и приводит ошибки к одному типу (`ApiError` с полями `status` и `message`), извлекая `message` из формата ошибок gateway `{ message }`;
- при наличии access-токена добавляет заголовок `Authorization: Bearer <token>`; без токена защищённый запрос не отправляется (используется только токен из состояния `AuthProvider`).

`fetch` покрывает потребности (JSON, заголовки, статусы) и не требует зависимости; axios дал бы интерсепторы, но для двух эндпоинтов это избыточно. Токен читается из аргумента/контекста, а не из модуля напрямую, чтобы HTTP-слой оставался тестируемым изолированно.

### 4. Доступ к gateway: dev-прокси Vite, базовый URL из переменной окружения

В `vite.config.js` добавляется `server.proxy`: префикс `/auth` проксируется на `process.env.GATEWAY_URL ?? 'http://localhost:8080'`. HTTP-клиент использует относительные пути (`/auth/login`), а базовый адрес берётся из `import.meta.env.VITE_API_BASE_URL` (по умолчанию пустая строка, то есть текущий origin).

Почему так: dev-сервер Vite (5173) и gateway (8080) — разные origin, поэтому прямой вызов без CORS невозможен. Прокси Vite решает это без изменения бэкенда (в отличие от альтернативы «включить CORS на gateway», которая выходит за рамки изменения и расширяет поверхность атаки). Абсолютный URL из env как основной вариант отклонён, так как требует CORS уже на этапе разработки. Настройка продового reverse-proxy/CORS — вне рамок (см. Open Questions).

### 5. Клиентская валидация: те же правила, что в gateway

Правила выносятся в чистые функции (`src/auth/validation.js`): email по тому же шаблону, что `RegistrationService.EMAIL_PATTERN`, и минимальная длина пароля 8 (константа `MINIMUM_PASSWORD_LENGTH = 8` в gateway). Валидация выполняется перед отправкой запроса и блокирует отправку при ошибке; сообщения показываются рядом с соответствующим полем.

Дублирование правил на клиенте — осознанный компромисс: пользователь получает мгновенную обратную связь без сетевого запроса, при этом gateway остаётся источником истины, а его сообщения об ошибках `400` по-прежнему отображаются в форме. Изменение правил в gateway потребует синхронизации констант; это фиксируется в рисках.

### 6. Отображение ошибок gateway

Маппинг ответов аутентификации (в `ApiError` → сообщение формы):

| Ответ gateway | Поведение веб-клиента |
| --- | --- |
| `409` (email занят) | сообщение «пользователь с таким email уже зарегистрирован» на форме регистрации |
| `400` (валидация) | текст `message` от gateway на соответствующей форме |
| `401` (неверные данные) | единое сообщение «неверный email или пароль», без указания конкретного поля |
| `5xx`/сетевая ошибка | сообщение о невозможности выполнить запрос; состояние аутентификации не меняется |
| `401` на защищённом запросе | удаление access-токена и переход на `/login` |

Сообщение `401` формируется на клиенте, а не берётся из `message` gateway, чтобы не зависеть от формулировки сервера и гарантированно не раскрывать, какой из параметров неверен.

### 7. После успешной регистрации — переход ко входу

Эндпоинт регистрации не возвращает токен, поэтому после успеха форма регистрации показывает подтверждение и ссылку/переход на `/login`; аутентифицированное состояние не устанавливается (иначе клиент показывал бы вход выполненным без токена). Автоматический вход после регистрации потребовал бы второго запроса к `/auth/login`; это возможное улучшение, но не требование текущих спеков.

### 8. Тесты: Vitest + Testing Library (jsdom)

Добавляются `vitest`, `jsdom`, `@testing-library/react`, `@testing-library/user-event`, `@testing-library/jest-dom`; конфигурация `test` добавляется в `vite.config.js` (`environment: 'jsdom'`, `include: ['test/**/*.test.{js,jsx}']`, `setupFiles: './test/setup.js'`), в `package.json` — скрипт `test`. Тесты мокают модуль `api` (никаких реальных вызовов gateway) и покрывают:

- чистые функции валидации (формат email, граничная длина пароля);
- HTTP-слой: формирование запроса, наличие/отсутствие заголовка `Authorization`, преобразование ошибок и `message` из ответа;
- формы: успех, ошибки `409`/`400`/`401`, блокировка повторной отправки, клиентская валидация;
- состояние аутентификации: вход, выход, восстановление из `localStorage`, защита маршрута.

`environment: 'jsdom'` выбран как стандарт для React Testing Library; браузерные e2e-тесты (Playwright) в изменение не входят.

### 9. Расположение тестов: отдельная папка `client/web/test/`

Тесты и setup-файл Vitest живут вне `src/`, в `client/web/test/**`, повторяя структуру исходного кода:

| Тестовый файл | Что покрывает |
| --- | --- |
| `test/setup.js` | matchers `@testing-library/jest-dom`, очистка DOM и `localStorage` после каждого теста |
| `test/api/client.test.js` | HTTP-слой: формирование запроса, заголовок `Authorization`, преобразование ошибок, `401` на защищённом запросе |
| `test/api/authApi.test.js` | контракт `POST /auth/register` и `POST /auth/login` |
| `test/auth/validation.test.js` | правила клиентской валидации email и пароля |
| `test/auth/AuthProvider.test.jsx` | вход, выход, восстановление сессии из `localStorage`, очистка состояния при `401` |
| `test/auth/RequireAuth.test.jsx` | защита аутентифицированного маршрута |
| `test/pages/LoginPage.test.jsx` | форма входа: успех, `401`, клиентская валидация, блокировка отправки, сетевая ошибка |
| `test/pages/RegisterPage.test.jsx` | форма регистрации: успех, `409`, `400`, `5xx`, клиентская валидация, блокировка отправки |
| `test/App.test.jsx` | маршруты, переходы между формами, email пользователя, выход |

Тесты импортируют продакшн-код по относительным путям (`../src/**`). Сборка `vite build` не подхватывает `test/**`, так как эти файлы нигде не импортируются, поэтому в бандл попадает только код приложения. `include` в конфигурации Vitest ограничен `test/**`, то есть новый тест, случайно созданный рядом с кодом в `src/**`, не будет запущен — договорённость становится явной и проверяемой.

Альтернатива — размещать тесты рядом с исходниками (`src/**/*.test.jsx`) — отклонена: она смешивает тесты и код в одной папке. Вариант `src/**/__tests__` отклонён по той же причине.

## Risks / Trade-offs

- **[Risk]** access-токен в `localStorage` доступен любому JS на странице (XSS-риск). **Mitigation**: не подключать сторонние скрипты, не логировать токен, не выводить его в UI; переход на httpOnly cookie с refresh-токеном — отдельное изменение, требующее доработки gateway (в Non-Goals).
- **[Risk]** Клиентская валидация дублирует правила gateway и может разойтись с ними. **Mitigation**: единый модуль валидации и константа минимальной длины пароля; тесты на граничные значения; серверные ошибки `400` всё равно отображаются в форме.
- **[Risk]** Dev-прокси Vite работает только в режиме разработки; в проде относительные пути требуют reverse-proxy к gateway. **Mitigation**: базовый URL параметризован через `VITE_API_BASE_URL`; вопрос продового размещения вынесен в Open Questions и не блокирует реализацию.
- **[Risk]** Нет refresh-токена, поэтому после истечения access-токена (1 час) пользователь разлогинивается. **Mitigation**: обработка `401` на защищённом запросе очищает токен и приводит на `/login` с понятным поведением; продление сессии — отдельное изменение.
- **[Risk]** Новые зависимости (`react-router-dom`, тестовый стек) могут конфликтовать с React 19 / Vite 8. **Mitigation**: использовать актуальные версии, совместимые с React 19; после установки проверить `npm run lint`, `npm run build` и `npm test`.
- **[Risk]** Текущий демонстрационный контент `App.jsx`/`App.css` удаляется, что меняет внешний вид приложения. **Mitigation**: изменение и так предполагает замену заглушки; стили переиспользуются для форм в минимальном объёме.
- **[Risk]** При переносе тестов можно оставить старый setup-файл в `src/` или указать неверный `setupFiles`/`include`, и `npm test` будет проходить, не запуская тестов. **Mitigation**: `include: ['test/**/*.test.{js,jsx}']` ограничивает запуск папкой `test/`; после переноса проверяется, что запускаются все 8 тестовых файлов и в `src/` не осталось `*.test.*` и `setup.js`.

## Migration Plan

Изменение затрагивает только фронтенд `client/web` и не переносит данные, поэтому миграция данных не требуется. Порядок развёртывания в dev-окружении:

1. Установить новые зависимости (`npm install` в `client/web`).
2. Запустить gateway (порт 8080) — существующее изменение `add-api-gateway-auth-routing`.
3. Запустить `npm run dev` в `client/web`; при нестандартном адресе gateway задать `GATEWAY_URL` для прокси.
4. Проверить сценарии: регистрация нового email, регистрация занятого email, вход с неверным паролем, успешный вход, перезагрузка страницы, выход.

Откат: изменение локализовано в фронтенде — достаточно откатить коммит (или восстановить предыдущий `App.jsx` и удалить добавленные модули); серверное состояние и данные пользователей не затрагиваются.

## Open Questions

- Где и как веб-клиент будет получать gateway в проде (reverse-proxy на том же origin, отдельный домен с CORS или gateway в роли статик-хоста)? Ответ влияет только на конфигурацию `VITE_API_BASE_URL`/инфраструктуру, не на спек, подход или задачи.
- Добавлять ли автологин после успешной регистрации (второй запрос к `/auth/login`)? Текущие спеки этого не требуют; решение можно принять отдельным изменением.
