## Why

Сейчас `client/web` — это базовое React-приложение Vite без какой-либо работы с пользователем, а `gateway` уже предоставляет `POST /auth/register` и `POST /auth/login` с выдачей JWT access-токена. Пользователь не может зарегистрироваться или войти через веб-интерфейс, поэтому единственный клиент продукта остаётся непригодным для сценариев с аутентификацией.

## What Changes

- Добавить в `client/web` форму регистрации (email + пароль), отправляющую запрос в gateway.
- Добавить в `client/web` форму входа (email + пароль), отправляющую запрос в gateway и получающую JWT access-токен.
- Добавить сохранение access-токена между перезагрузками страницы и аутентифицированное состояние с возможностью выхода.
- Добавить отображение ошибок gateway (409 при занятом email, 400 при невалидных данных, 401 при неверных учётных данных) в формах.
- Добавить клиентскую валидацию полей до отправки запроса (корректность email, минимальная длина пароля).
- Добавить маршрутизацию страниц (`/login`, `/register`, защищённый `/`) с перенаправлением неаутентифицированного пользователя на вход.
- Настроить dev-прокси Vite для путей `/auth/*` на gateway, чтобы разработка не требовала CORS на бэкенде.
- Добавить в `client/web` тестовую инфраструктуру (Vitest + Testing Library) и юнит-тесты форм и API-клиента.
- **BREAKING**: отсутствует — `client/web` не содержит пользовательских сценариев, breaking change не применим.

## Capabilities

### New Capabilities
- `web-user-auth`: регистрация, вход, хранение access-токена, выход из системы и отображение ошибок аутентификации в веб-клиенте.

### Modified Capabilities
_(нет — поведение `gateway-user-auth` и `gateway-request-routing` не меняется, веб-клиент использует уже существующие эндпоинты gateway)_

## Impact

- Затронутый код: `client/web/src/**` (новые страницы, компоненты форм, API-клиент, контекст аутентификации), `client/web/test/**` (юнит-тесты и setup-файл Vitest — тесты размещаются отдельно от исходного кода), `client/web/package.json` (новые зависимости), `client/web/vite.config.js` (dev-прокси, конфигурация тестов).
- Новые зависимости фронтенда: `react-router-dom` (маршрутизация), `vitest`, `@testing-library/react`, `@testing-library/user-event`, `jsdom` (тесты).
- Внешние API: используются существующие `POST /auth/register` и `POST /auth/login` gateway; новых эндпоинтов и изменений `backend/**` изменение не требует.
- Форматы контракта, на которые опирается клиент: тело запроса `{ email, password }`, ответ логина `{ accessToken, tokenType, expiresIn }`, ответ регистрации `{ id, email }`, ошибки в виде `{ message }`.
- Конфигурация: базовый URL gateway задаётся через dev-прокси Vite (по умолчанию `http://localhost:8080`) с возможностью переопределения через переменную окружения.
- Риск: access-токен хранится в браузере, поэтому для дальнейших защищённых запросов клиент должен отправлять `Authorization: Bearer <accessToken>`; политика обновления истёкшего токена (refresh) вне рамок этого изменения.
