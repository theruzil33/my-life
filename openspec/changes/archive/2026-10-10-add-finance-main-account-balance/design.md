## Context

См. `proposal.md` — Why и `specs/` — требования. В `backend/finance` уже есть вертикальные срезы счетов (`account/Account`, таблица `finance_accounts`), категорий (`category/Category` с полем `type` — `INCOME`/`EXPENSE`) и операций (`operation/Operation`, таблица `finance_operations` с `user_id`, `category_id`, `operation_date`, `amount`). Учётные данные пользователя приходят из `UserIdFilter` (заголовок `X-User-Id`), ошибки маппит `GlobalExceptionHandler` (`400` — `InvalidAccountDataException`, `404` — `AccountNotFoundException`, `409` — `CategoryInUseException`/`DataIntegrityViolationException`). Flyway: `baseline-version=1`, последняя миграция — `V5__create_finance_operations_table.sql`; прод — PostgreSQL (`ddl-auto=validate`), тесты — H2 в режиме PostgreSQL.

Операции сейчас на уровне требований `finance-operations` не привязаны к счёту и не меняют счета. Веб-клиент: `src/finances/AccountsTab.jsx` рисует список (название + начальная сумма) и модальное удаление, `src/finances/AccountFormModal.jsx` — создание, `src/api/financeApi.js` — вызовы `/finances/accounts`.

## Goals / Non-Goals

**Goals:**

- Связать операции со счётом через признак «главный»: финальная сумма главного счёта = начальная сумма + Σ приход − Σ уход по всем операциям пользователя.
- Автоматически делать первый счёт главным, запрещать второй главный счёт (`400`) и удаление главного счёта (`409`).
- Отдавать клиенту финальную сумму и признак главного счёта; показать их на странице счетов и дать выбрать признак при создании.
- Сохранить обратную совместимость миграцией: у существующих пользователей со счетами назначить главным самый ранний счёт.

**Non-Goals:**

- Не хранить `account_id` в операции и не менять сущность/контракт операций.
- Не давать редактировать счёт (в том числе менять признак главного) после создания и не добавлять «переключение» главного счёта.
- Не менять категории, gateway, аутентификацию и контракты операций.
- Не вводить валюту, переводы между счетами и историю баланса.

## Decisions

1. **Признак главного счёта — колонка `is_main BOOLEAN NOT NULL DEFAULT FALSE` в `finance_accounts`, отдельная миграция `V6__add_is_main_to_finance_accounts.sql`.** Существующие применённые миграции не правим (checksum Flyway). Миграция добавляет колонку и backfill: для каждого пользователя самым ранним (наименьший `id`) счётом помечается главный:
   ```sql
   ALTER TABLE finance_accounts ADD COLUMN is_main BOOLEAN NOT NULL DEFAULT FALSE;
   UPDATE finance_accounts a SET is_main = TRUE
   WHERE a.id = (SELECT MIN(b.id) FROM finance_accounts b WHERE b.user_id = a.user_id);
   ```
   Альтернатива «отдельная таблица настроек пользователя» отклонена как избыточная для одного флага.

2. **Не более одного главного счёта обеспечивается сервисом, а не частичным уникальным индексом.** PostgreSQL позволил бы `CREATE UNIQUE INDEX ... (user_id) WHERE is_main`, но тесты Flyway гоняются на H2, который частичные индексы не поддерживает; миграция с таким индексом сломала бы тесты. Поэтому проверка «главный уже есть» выполняется в `AccountService` до сохранения. Альтернатива «уникальный индекс `(user_id, is_main)`» отклонена: запретил бы более одного неглавного счёта.

3. **Финальная сумма вычисляется на чтение и не хранится.** `AccountService` переиспользует `OperationRepository`: сумма операций прихода и сумма операций ухода пользователя получаются агрегатным запросом с join на категорию:
   ```java
   @Query("select coalesce(sum(o.amount), 0) from Operation o join Category c on o.categoryId = c.id "
           + "where o.userId = :userId and c.type = :type")
   BigDecimal sumAmountByUserIdAndCategoryType(@Param("userId") Long userId, @Param("type") CategoryType type);
   ```
   Финальная сумма главного счёта = `initialAmount + income − expense`; неглавного — `initialAmount`. Вычисление выполняется и при создании (у пользователя уже могли быть операции до появления первого счёта), и при чтении списка. Хранить баланс в счёте отклонено: он менялся бы при каждом upsert/удалении операции и рассинхронизировался бы; требования `finance-operations` (операции не меняют начальные суммы) сохраняются.

4. **Создание: форсирование и запрет второго главного.** `AccountRequest` получает необязательное `Boolean isMain` (по умолчанию «ложь»). Логика `create`:
   - `boolean hasAccounts = accountRepository.existsByUserId(userId);`
   - `boolean requestedMain = Boolean.TRUE.equals(request.isMain());`
   - если `!hasAccounts` → `isMain = true` (первый счёт всегда главный);
   - иначе если `requestedMain` → `isMain = true` (главного ещё нет в корректных данных) — но перед этим проверяется `existsByUserIdAndIsMainTrue(userId)`; при наличии главного запрос отклоняется `InvalidAccountDataException` (`400`).
   Альтернатива «при запросе второго главного снимать признак со старого» (демоушен) отклонена пользователем: выбран явный отказ.

5. **Контракт счетов:**
   - `POST /accounts` — тело `{ "name", "initialAmount", "isMain"? }`; ответ `201` с `{ "id", "name", "initialAmount", "finalAmount", "isMain" }`.
   - `GET /accounts` — список `{ "id", "name", "initialAmount", "finalAmount", "isMain" }`; суммы прихода/ухода считаются один раз на список.
   - `DELETE /accounts/{id}` — без изменений; главный счёт даёт `409`.
   Контекст сервиса `/finances` даёт клиенту пути `/finances/accounts`.

6. **Удаление главного счёта — новое исключение `account/MainAccountDeletionException`, маппится в `409`.** `AccountService.delete` после поиска собственного счёта проверяет `account.isMain()` и бросает исключение до удаления. Чужой/несуществующий счёт по-прежнему даёт `404` (проверка владения идёт первой). Регистрируется обработчик в `GlobalExceptionHandler`.

7. **Сущность и репозиторий счетов.** `Account` получает поле `isMain` и геттер `isMain()`, конструктор — параметр `isMain`. `AccountRepository` получает `boolean existsByUserId(Long userId)` и `boolean existsByUserIdAndIsMainTrue(Long userId)`; `findByUserIdOrderById` сохраняется. Сеттеров нет — счёт неизменяем, что соответствует требованиям.

8. **Веб-клиент: финальная сумма, пометка главного, выбор при создании.**
   - `financeApi.create` передаёт `isMain` в тело; `financeApi` не меняет прочие методы.
   - `AccountsTab` показывает `finalAmount` (форматирование `Number(value).toFixed(2)` как сейчас), выводит пометку «главный» у счёта с `isMain === true`, для главного счёта не выводит кнопку удаления.
   - `AccountFormModal` добавляет чекбокс «Сделать счётом главным» и передаёт `isMain` в `onSubmit`; существующая валидация названия/суммы не меняется.
   - Используются существующие классы (`accounts-list`, `account-item`, `account-name`, `account-amount`, `modal-*`, `auth-field`); в `App.css` добавляются минимальные правила для пометки главного счёта.
   Альтернатива «показывать и начальную, и финальную сумму» отклонена для простоты: показывается финальная сумма (для неглавных она равна начальной).

9. **Обработка конфликта на клиенте.** Если API всё же вернёт `409` при удалении (устаревшее состояние), `AccountsTab` покажет сообщение об ошибке и оставит счёт в списке — существующий путь `actionError` переиспользуется без изменений.

## Risks / Trade-offs

- **[Risk]** Гонка: два одновременных создания первого счёта могут дать двух главных (нет уникального индекса из-за H2). **Mitigation:** проверка в сервисе закрывает штатный случай; при необходимости позже можно добавить частичный уникальный индекс отдельной миграцией только для PostgreSQL. Риск редкий (создание первого счёта одним пользователем).
- **[Risk]** Существующие пользователи со счетами получают главный счёт лишь через backfill миграции; если backfill не выполнится, операции ни к чему не применятся. **Mitigation:** backfill в `V6` назначает самый ранний счёт главным для каждого пользователя; покрывается тестом миграции/репозитория.
- **[Risk]** Агрегатный JPQL с `join ... on` между `Operation` и `Category` может не поддержаться диалектом. **Mitigation:** Hibernate 6 поддерживает ad-hoc join по не связанным сущностям; при проблемах запасной вариант — выборка операций пользователя и суммирование в сервисе по типу категории (категории пользователя уже читаются). Проверяется unit- и web-тестами.
- **[Risk]** Сумма может уходить в минус (уходов больше, чем приходов и начальной суммы). **Mitigation:** отрицательная финальная сумма допустима и отображается как есть; требование не запрещает отрицательный баланс.
- **[Risk]** Нельзя сменить главный счёт и удалить его — пользователь «заперт» на первом счёте. **Mitigation:** осознанное решение пользователя для простоты; отдельного сценария смены главного счёта в изменении нет.

## Migration Plan

1. Задеплоить `finance` с `V6__add_is_main_to_finance_accounts.sql` (колонка + backfill), изменёнными DTO/сервисом/контроллером счетов, агрегатом в `OperationRepository` и обработчиком `409`. Существующие счета получают главный счёт автоматически; операции и категории не затрагиваются.
2. Задеплоить `web` с финальной суммой, пометкой главного счёта, выбором «главный» при создании и отключённым удалением главного счёта.

Откат: убрать признак главного счёта на клиенте и вернуть отображение начальной суммы; снять проверки главного счёта и агрегат баланса в сервисе. Колонку `is_main` можно оставить (не используется) либо удалить отдельной миграцией.
