## Context

См. `proposal.md` — Why и `specs/` — требования. В `backend/finance` уже есть вертикальные срезы счетов и категорий: сущности `account/Account` (`finance_accounts`) и `category/Category` (`finance_categories`), репозитории, сервисы, контроллеры, DTO, `UserIdFilter` (заголовок `X-User-Id`, атрибут `finance.userId`), `ApiError` и `GlobalExceptionHandler`. Flyway использует `baseline-version=1`, последняя миграция — `V4__add_group_name_to_finance_categories.sql`. Контекст сервиса — `/finances` (порт 8082), а gateway проксирует префикс `/finances` и проставляет `X-User-Id`, поэтому отдельных маршрутов gateway не требуется.

На веб-клиенте `src/pages/FinancesPage.jsx` содержит вкладки «Счета»/«Категории» и лениво открывает содержимое; логика вкладки категорий — в `src/finances/CategoriesTab.jsx` (загрузка, модальные окна, состояния загрузки/ошибки/пусто), работа с API — в `src/api/financeApi.js` через `src/api/client.js` (`request`, `requiresAuth: true`, CSRF для изменяющих методов). Константы типов категорий — в `src/finances/categoryOptions.js`. Формат матрицы и выбор диапазона уже есть в `src/tracker/StatisticsTab.jsx` (таблица `stats-matrix`, горизонтальная прокрутка `stats-scroll`, поля `type="date"` и валидация диапазона).

## Goals / Non-Goals

**Goals:**

- Добавить в `finance` учёт операций: одну запись на пару «категория + дата», upsert суммы, чтение за дату и за диапазон, удаление.
- Гарантировать целостность: операция ссылается на категорию владельца; категорию с операциями удалить нельзя (`409`).
- Дать веб-клиенту вкладки «Операции» (ввод сумм по дате) и «Статистика» (матрица категории × даты), переиспользуя существующие паттерны UI.
- Оставить счета, аутентификацию, gateway и контракты категорий/счетов без изменений (кроме запрета удаления категории с операциями).

**Non-Goals:**

- Не связывать операции со счетами и не менять начальные суммы счетов.
- Не моделировать валюту, знак суммы, переводы, планирование или повторяющиеся операции.
- Не давать операциям отдельное редактирование сверх upsert по паре «категория + дата».
- Не менять сортировку категорий, возвращаемую API (`/categories` остаётся «приход → уход»).

## Decisions

1. **Новая таблица `finance_operations` отдельной миграцией `V5__create_finance_operations_table.sql`.** Колонки по образцу существующих: `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, `user_id BIGINT NOT NULL`, `category_id BIGINT NOT NULL REFERENCES finance_categories(id)`, `operation_date DATE NOT NULL`, `amount NUMERIC(19,2) NOT NULL`, `created_at`/`updated_at TIMESTAMP WITH TIME ZONE NOT NULL`. Индексы: `idx_finance_operations_user_id (user_id)` и `idx_finance_operations_user_id_date (user_id, operation_date)`. Уникальность пары обеспечивается `UNIQUE (category_id, operation_date)`: категория принадлежит ровно одному пользователю, поэтому уникальность по категории и дате не смешивает пользователей. Отдельная миграция (а не правка применённых `V2`–`V4`) — из-за Flyway checksum.

2. **Операция хранит только `categoryId`, `date`, `amount`; тип не дублируется.** Тип (приход/уход) выводится из категории, а тип категории неизменяем, поэтому значение стабильно. Дублирование `type` в операции создало бы риск рассинхронизации и не нужно ни одному сценарию. Альтернатива «хранить `type` для быстрых чтений» отклонена: выборки идут по пользователю и датам, а тип категории и так дёшево доступен.

3. **Дата — `java.time.LocalDate` (календарная дата без времени и зоны).** Операции привязаны к календарному дню, а не моменту времени, поэтому часовые пояса не влияют на поведение. В JSON — строка ISO `yyyy-MM-dd` средствами `jackson-datatype-jsr310` (входит в Spring Boot). Альтернатива «`Instant`/`LocalDateTime`» отклонена: внесла бы неоднозначность зоны.

4. **Upsert реализуется в сервисе: find → update | create.** `OperationService.save(userId, request)` проверяет вход, находит категорию через `CategoryRepository.findByIdAndUserId` (`404`, если не найдена), затем `OperationRepository.findByCategoryIdAndOperationDate`; при наличии обновляет `amount`, иначе создаёт запись. На время сохранения пары опирается `UNIQUE (category_id, operation_date)`; гонка приводит к `DataIntegrityViolationException`, которую обрабатывают повторным поиском и обновлением (idempotent upsert). Альтернатива «сначала delete+insert» отклонена: теряет `created_at` и плодит лишние удаления.

5. **REST-контракт операций:**
   - `GET /operations?date=YYYY-MM-DD` — операции за дату (вкладка «Операции»);
   - `GET /operations?from=YYYY-MM-DD&to=YYYY-MM-DD` — операции за диапазон включительно (вкладка «Статистика»);
   - `PUT /operations` с телом `{ "categoryId", "date", "amount" }` — upsert, ответ `200` с `{ "id", "categoryId", "date", "amount" }`;
   - `DELETE /operations/{id}` — `204` без тела.
   Контекст-путь сервиса `/finances` даёт клиенту пути `/finances/operations...`. Один `OperationController` различает одиночную дату и диапазон по наличию параметров `date` или `from`/`to`. Альтернатива «POST `/operations` для создания и отдельный PUT для обновления» отклонена: клиенту нужен один идемпотентный вызов на пару «категория + дата».

6. **DTO и валидация.** `OperationRequest(Long categoryId, LocalDate date, BigDecimal amount)` и `OperationResponse(Long id, Long categoryId, LocalDate date, BigDecimal amount)`. Валидация по образцу `AccountService`: `categoryId` и `date` обязательны; `amount` обязателен, `> 0`, `scale() <= 2`. Диапазон: обе границы обязательны и `from <= to`. Собственные исключения `operation/InvalidOperationDataException` (`400`) и `operation/OperationNotFoundException` (`404`) регистрируются в `GlobalExceptionHandler`; ненайденная/чужая категория даёт `CategoryNotFoundException` (`404`).

7. **Запрет удаления категории с операциями — сервисная проверка + FK.** В `CategoryService.delete` перед удалением добавляется `operationRepository.existsByCategoryId(categoryId)`; при наличии операций бросается `category/CategoryInUseException` (`409`), маппится в `GlobalExceptionHandler`. FK `category_id → finance_categories(id)` (без `ON DELETE CASCADE`) дополнительно защищает БД. Репозиторий операций инжектируется в `CategoryService`; это единственная правка существующей логики категорий. Альтернатива «полагаться только на FK» отклонена: нужно предсказуемое `409` с телом `ApiError`.

8. **Порядок «расход → приход» задаёт клиент.** API возвращает операции и категории без требований к порядку группировки (`/categories` по-прежнему «приход → уход»). Вкладки «Операции» и «Статистика» строят строки, сортируя категории по типу (`EXPENSE` первым, затем `INCOME`), внутри типа — по порядку ответа API (`id`). Это соответствует явному требованию пользователя для вкладки «Операции»; для «Статистики» порядок принят таким же для единообразия фичи.

9. **Вкладка «Операции» — компонент с локальным черновиком суммы на строку.** `OperationsTab` хранит выбранную дату (`LocalDate`, по умолчанию сегодня; `<input type="date">` без `max` — прошлое и будущее разрешены), загружает категории и операции за дату, строит строки «категория + поле суммы». Поле показывает сумму существующей операции или пусто. Ввод подтверждается по `blur`/Enter: значение нормализуется (запятая → точка), затем сохраняется (upsert) при изменении; невалидное значение не отправляется и показывает причину. Очистка поля у категории с операцией открывает подтверждение и по подтверждению удаляет операцию (`DELETE`), при отмене восстанавливает прежнюю сумму. Во время запроса строка блокируется. Перезагрузка не требуется — состояние строки обновляется локально из ответа, что сохраняет введённые значения остальных строк. **Визуальная группировка** выполняется как на вкладке «Категории»: в пределах одного типа категории с одинаковым непустым `group` собираются в блок с рамкой (`category-group`/`category-group-framed`) и заголовком (`category-group-title`), внутри блока категории идут в порядке ответа API; категории без группы показываются отдельными строками без заголовка. Блоки упорядочиваются по первому появлению их категорий в ответе API внутри типа, а так как типы идут «расход → приход», блоки ухода предшествуют блокам прихода. Блок не смешивает типы (разбиение по типам). Группировка только визуальная и MUST NOT менять состав или порядок данных API; строки сохраняют классы `operation-row`/`operation-amount` для поля суммы.

10. **Вкладка «Статистика» — матрица `категории × даты` с визуальной группировкой.** `StatisticsTab` хранит диапазон (по умолчанию — весь текущий календарный месяц, с первого по последнее число), поля `type="date"` (без `max` — будущие даты допустимы), кнопку «Применить» и валидацию (`from`, `to` заданы, `from <= to`). Данные берутся одним запросом `GET /operations?from&to` плюс список категорий. Таблица строится с дополнительной левой колонкой группировки: в пределах одного типа категории с одинаковым непустым `group` образуют группу — ячейка с названием группы имеет `rowspan` по числу строк группы и вертикально центрируется (`vertical-align: middle`), а строки категорий идут справа как части группы; категория без группы занимает отдельную строку, её ячейка названия растягивается на обе левые колонки (`colspan="2"`). Группы упорядочиваются по первому появлению в ответе API внутри типа, типы — «уход → приход»; группа не смешивает типы (разбиение по типам). Ячейки таблицы имеют видимые границы (`border`), чтобы облегчить чтение. Столбцы дат занимают всю доступную ширину (`width: 100%`, равномерное распределение), а при нехватке ширины таблица прокручивается горизонтально через существующий `stats-scroll` (`overflow-x: auto`). Скролл-контейнер `stats-scroll` сохраняет горизонтальную прокрутку, но MUST NOT ограничивать высоту (нет `max-height`) и MUST NOT создавать вложенную вертикальную прокрутку: таблица рендерится на полную высоту, а вертикально прокручивается только страница браузера. Чтобы горизонтальная полоса прокрутки не перекрывала последнюю строку (особенно при overlay-скроллбарах), у контейнера `.finances-tab .stats-scroll` резервируется место снизу (`padding-bottom`/`scrollbar-gutter`). Если категорий нет — пустое состояние. Состав и порядок данных API не меняются — группировка только визуальная.

11. **`financeApi` расширяется методами операций.** Добавляются `listOperationsByDate(token, date)`, `listOperationsByRange(token, from, to)`, `saveOperation(token, { categoryId, date, amount })` (`PUT`) и `removeOperation(token, id)` (`DELETE`) со `requiresAuth: true`; изменяющие методы автоматически получают CSRF через `client.js`. Дополнительной настройки передачи учётных данных не требуется.

12. **Стили и модальное подтверждение переиспользуются.** Используются существующие классы (`tracker-tabs`, `tracker-tab`, `finances-tab`, `login-form`/`auth-field`, `modal-overlay`/`modal`, `tracker-error`, `tracker-status`, `tracker-empty`, `stats-scroll`); в `App.css` добавляются минимальные правила для строк операций и матрицы статистики.

13. **Открытие вкладки перечитывает данные.** `FinancesPage` передаёт каждой открытой вкладке признак активности (`isActive`), а `OperationsTab`/`StatisticsTab` перечитывают категории и операции при переходе вкладки из неактивного состояния в активное (Statistics — для применённого диапазона, Operations — для выбранной даты). Это отражает изменения, сделанные на других вкладках (например, добавленную категорию), без ремоунта и без потери локального состояния. Альтернатива «размонтировать вкладку при уходе» отклонена: теряет применённый диапазон статистики и черновики ввода операций; альтернатива «общий кэш/событийная шина» отклонена как избыточная для двух вкладок.

## Risks / Trade-offs

- **[Risk]** Гонка при одновременном upsert одной пары может дать `DataIntegrityViolationException`. **Mitigation:** уникальный ключ + обработка нарушения повторным поиском и обновлением (идемпотентный upsert).
- **[Risk]** Большой диапазон в статистике (например, год) даёт сотни колонок и тяжёлую таблицу. **Mitigation:** горизонтальная прокрутка (`stats-scroll`) и один запрос за диапазон; серьёзные пределы не вводятся, так как требование не ограничивает диапазон.
- **[Risk]** FK `category_id` может сломать существующий сценарий удаления категории, если сервисная проверка не сработает. **Mitigation:** сначала сервисная проверка `existsByCategoryId` → `409`; FK остаётся страховкой, а его нарушение маппится в `409`.
- **[Risk]** Пользователь вводит сумму с запятой или пробелами, а API ожидает число. **Mitigation:** клиент нормализует ввод (запятая → точка, обрезка пробелов) и валидирует `> 0` и `<= 2` знаков до отправки; сервер — источник истины.
- **[Risk]** Разные требования к порядку: `/categories` отдаёт «приход → уход», а новые вкладки показывают «расход → приход». **Mitigation:** сортировка выполняется только на клиенте и не меняет контракт API; это осознанное решение для фичи операций.
- **[Risk]** Удаление операции по очистке поля может быть случайным. **Mitigation:** обязательное подтверждение с восстановлением прежней суммы при отмене или ошибке.

## Migration Plan

1. Задеплоить `finance` с миграцией `V5__create_finance_operations_table.sql` (таблица `finance_operations`, индексы, FK, уникальность), эндпоинтами `/operations` и запретом удаления категории с операциями. Существующие счета/категории не затрагиваются; операций ещё нет, поэтому все категории удаляются как раньше.
2. Задеплоить `web` с новыми вкладками «Операции» и «Статистика» и методами `financeApi`.

Откат: убрать вкладки и методы операций на клиенте; снять контроллер/сервис/репозиторий операций и проверку `existsByCategoryId` в сервисе категорий. Таблицу `finance_operations` можно оставить (не используется) либо удалить отдельной миграцией; удаление таблицы уничтожает введённые операции.
