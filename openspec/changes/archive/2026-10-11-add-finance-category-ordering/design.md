## Context

См. `proposal.md` — Why. В `backend/finance` категория хранится в `category/Category` (таблица `finance_categories`, последняя миграция Flyway — `V8`). Контракт категории — `CategoryRequest`/`CategoryResponse` с полями `type`, `name`, `group`, `plannedAmount`. Список категорий (`CategoryService.list`) читается через `CategoryRepository.findByUserIdOrderById` и сортируется в памяти компаратором `TYPE_THEN_ID` (`INCOME` → `EXPENSE`, затем по возрастанию `id`). Контроллер `web/CategoryController` отдаёт CRUD по `/categories` под `UserIdFilter`, gateway маршрутизирует префикс `/finances` — отдельной настройки маршрута не требуется.

На клиенте вкладка «Категории» (`client/web/src/finances/CategoriesTab.jsx`) собирает блоки по группе через `buildBlocks`, используя порядок ответа API. Вкладки «Операции» (`OperationsTab.jsx`) и «Статистика» (`StatisticsTab.jsx`) содержат собственный компаратор `orderCategories`, который дополнительно сортирует категории одного типа по возрастанию `id`, — именно он переопределяет пользовательский порядок. Запросы идут через `src/api/financeApi.js` и общий `request`.

## Goals / Non-Goals

**Goals:**

- Хранить и отдавать пользовательский порядок категорий отдельно для прихода и ухода, не меняя остальные атрибуты категории, операции и баланс.
- Дать пользователю перемещать блоки (именованную группу целиком или одиночную категорию) на вкладке «Категории» кнопками «выше»/«ниже».
- Обеспечить единый порядок категорий внутри типа на всех трёх вкладках финансов.
- Сохранить относительный порядок типов на каждой вкладке: приход перед уходом на «Категориях», уход перед приходом на «Операциях» и «Статистике».

**Non-Goals:**

- Не менять группировку по названию группы, её визуальное оформление и правила объединения блоков.
- Не вводить drag-and-drop и не добавлять сторонние библиотеки — только кнопки перемещения.
- Не менять контракты операций, баланса и gateway; не добавлять порядок в `CategoryRequest`/`CategoryResponse`.
- Не реализовывать перемещение отдельной категории внутри группы: группа перемещается целиком (решение пользователя).

## Decisions

1. **Порядок хранится как `sort_order INTEGER NOT NULL` в `finance_categories` через миграцию `V9__add_sort_order_to_finance_categories.sql`.** Колонка добавляется nullable, заполняется существующим порядком по `id` внутри пары `(user_id, type)` через `ROW_NUMBER() OVER (PARTITION BY user_id, type ORDER BY id)`, затем переводится в `NOT NULL`. Правка уже применённых миграций сломала бы checksum Flyway. Альтернатива «отдельная таблица порядка» отклонена: порядок — это ровно один целочисленный атрибут категории, отдельная сущность не нужна.

2. **Область порядка — пара `(user_id, type)`.** Числовые значения `sort_order` уникальны и последовательны внутри типа пользователя; порядок прихода и ухода независим. Тип категории по-прежнему определяет раздел, а не позицию.

3. **В `Category` появляется поле `Integer sortOrder` с геттером; конструктор создания и `edit` его не меняют.** `edit` (название/группа/план) MUST NOT затрагивать порядок. Новое значение назначается отдельным методом/логикой изменения порядка, чтобы редактирование категории не сбрасывало её позицию.

4. **Новая категория получает `sort_order = max(sort_order) + 1` для своей пары `(user_id, type)`.** Значение вычисляется в `CategoryService.create` через запрос репозитория (например, `findMaxSortOrder(userId, type)`); при отсутствии категорий — `1`. Это реализует требование «новая категория идёт в конец своего типа».

5. **Список остаётся сортировкой в памяти.** `CategoryRepository` получает метод выборки по пользователю, а `CategoryService.list` заменяет компаратор `TYPE_THEN_ID` на `TYPE_THEN_ORDER_THEN_ID`: `INCOME` → `EXPENSE`, затем по `sortOrder`, затем по `id`. Сортировка по `id` как второй ключ сохраняет детерминированность при равных/отсутствующих значениях. Альтернатива «сортировать в SQL по строковому типу» отклонена: строки `INCOME`/`EXPENSE` сортируются не в желаемом порядке, а `INCOME`-первым легче выразить в сервисе.

6. **Новый эндпоинт `PUT /finances/categories/order`** с телом `{ type, categoryIds }`, где `categoryIds` — полный упорядоченный список идентификаторов всех категорий пользователя указанного типа. Полная замена набора снимает неоднозначность частичного порядка. Регистрация маршрута до `/{id}` не нужна: Spring сопоставляет `order` со строковым путём, но во избежание конфликта с `PUT /{id}` путь фиксирован как литерал.

7. **Валидация изменения порядка в `CategoryService` (новый метод `reorder`):**
   - тип MUST быть `INCOME` или `EXPENSE`, иначе `InvalidCategoryDataException` (`400`);
   - дубликаты в `categoryIds` — `InvalidCategoryDataException` (`400`);
   - для каждого идентификатора: отсутствующий у пользователя (чужой или несуществующий) — `CategoryNotFoundException` (`404`); категория другого типа — `InvalidCategoryDataException` (`400`);
   - набор идентификаторов MUST совпадать с полным набором категорий пользователя этого типа (нет пропусков) — иначе `InvalidCategoryDataException` (`400`);
   - при успехе каждому идентификатору присваивается `sort_order` по его индексу (`1..n`).

8. **Изменение порядка идёт через отдельный DTO `CategoryOrderRequest(String type, List<Long> categoryIds)`** в `category/dto`; ответ — `204 No Content`, так как состояние возвращает последующий список. Альтернатива «отдавать обновлённый список» отклонена: клиент и так читает список и хочет минимизировать контракт.

9. **Клиент на вкладке «Категории» строит блоки как раньше, но добавляет кнопки перемещения и вычисляет новую плоскую нумерацию.** По нажатию «выше»/«низ» `CategoriesTab.jsx`:
   - формирует список категорий своего типа в новом порядке блоков, сохраняя порядок категорий внутри перемещаемого блока;
   - вызывает `financeApi.reorderCategories(accessToken, type, ids)`;
   - при успехе применяет новый порядок к состоянию (перечитывание списка или локальная перестановка), при ошибке показывает сообщение и не меняет порядок;
   - на время запроса блокирует повторные перемещения.
   Кнопки «вверх» первого блока типа и «вниз» последнего блока типа отключаются. Альтернатива «оптимистичное обновление с откатом» отклонена: применение порядка только по успешному ответу проще и напрямую соответствует требованию «при ошибке порядок не меняется».

10. **`OperationsTab.jsx` и `StatisticsTab.jsx` перестают сортировать по `id`.** Компаратор `orderCategories` в обоих файлах заменяется на сортировку только по типу (`EXPENSE` → `INCOME`), а относительный порядок внутри типа берётся из ответа API (стабильная сортировка массивов в JS сохраняет исходный порядок). Существующие `buildBlocks` и группировка не меняются.

11. **`client/web/src/api/financeApi.js` получает метод `reorderCategories(token, type, categoryIds)`** (`PUT /finances/categories/order`). Валидация порядка на клиенте не требуется: список идентификаторов формируется из уже загруженных категорий.

12. **Стили.** Кнопкам перемещения назначаются существующие классы действий (`habit-action`) и, при необходимости, новый класс в `src/App.css`; сетка блока категории расширяется на колонку с кнопками, чтобы строки оставались выровненными.

## Risks / Trade-offs

- **[Risk]** Полная замена набора при изменении порядка ломается при одновременном создании категории в другом запросе. **Mitigation:** приложение однопользовательское, а вкладка перечитывает список перед перемещением; несовпадение набора даёт `400`, и клиент показывает ошибку, не меняя порядок.
- **[Risk]** Существующий `PUT /categories/{id}` может конфликтовать с литеральным `/categories/order`. **Mitigation:** Spring сопоставляет точный литерал приоритетнее шаблона с переменной; путь задаётся как `PUT /categories/order`, а тест `CategoryControllerTest` проверяет оба маршрута.
- **[Risk]** Заполнение `sort_order` на проде может дать неверный стартовый порядок, если у пользователя категории уже перемешивались. **Mitigation:** backfill воспроизводит текущий порядок по `id`, то есть поведение до изменения; порядок `INCOME`/`EXPENSE` сохраняется.
- **[Risk]** Правка `edit` без изменения порядка может оставить категорию «не на месте» при смене группы. **Mitigation:** это осознанно (Non-Goal) — блок определяется первым появлением в списке, а пользователь при необходимости перемещает блок вручную.
- **[Risk]** Кнопки перемещения добавляют колонку в строку блока и могут нарушить выравнивание. **Mitigation:** сетка и стили обновляются в одной задаче с тестами отображения блока.

## Migration Plan

1. Задеплоить `finance` с миграцией `V9__add_sort_order_to_finance_categories.sql` (backfill по `id`), полем `sortOrder`, новым эндпоинтом порядка и сортировкой списка. Существующие категории сохраняют текущий порядок; операции, баланс и план не меняются.
2. Задеплоить `web` с кнопками перемещения на вкладке «Категории» и отказом от сортировки по `id` на вкладках «Операции» и «Статистика».

Откат: вернуть сортировку по `id` в сервисе и на клиенте, убрать кнопки перемещения и вызов эндпоинта. Колонка `sort_order` остаётся в БД (не используется).
