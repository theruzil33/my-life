## Context

Сервис `tracker` уже хранит активности в `tracker_habits`, дни недели — в `tracker_habit_weekdays`, а отметки — в `tracker_habit_completions` с уникальностью `(habit_id, completed_on)`. Активность попадает в список и историю по правилам `Habit.isScheduledOn`, а отметка всегда одна на дату.

CSV-импорт (`ProductivityCsvParser`) сейчас включает любой непустой вариант из второго столбца в название: «Чистил зубы (Утром)» и «Чистил зубы (Вечером)» становятся двумя активностями. В выгрузке пользователя варианты «Утром»/«Вечером» означают части дня одной активности, а «На работе»/«Дома» — действительно разные варианты.

Веб-клиент получает список на дату и историю, рисует по одной строке на активность и по одному чекбоксу на дату.

## Goals / Non-Goals

**Goals:**

- Добавить активностям необязательный набор частей дня `MORNING`/`DAY`/`EVENING` (до трёх, без повторов).
- Сделать отметку выполнения независимой для каждой части дня, сохранив общий режим для активностей без частей дня.
- Перенести строки CSV с вариантами «Утром»/«Днём»/«Вечером» в одну активность с частями дня.
- Сохранить существующие активности и отметки без потери данных и без обязательной миграции расписаний.

**Non-Goals:**

- Произвольное время (часы и минуты), временные диапазоны и напоминания.
- Отдельная периодичность или дата начала для каждой части дня — расписание остаётся общим для активности.
- Автоматическое переименование уже существующих активностей вида «… (Утром)» в активность с частями дня — пользователь может настроить части дня вручную.
- Изменения в gateway.

## Decisions

### 1. Части дня хранятся отдельной таблицей-коллекцией

Новая таблица `tracker_habit_time_of_day (habit_id, time_of_day)` с первичным ключом по обеим колонкам и каскадным удалением. Это повторяет уже используемый приём для `tracker_habit_weekdays` и не меняет таблицу активностей.

Альтернатива с тремя булевыми колонками в `tracker_habits` быстрее читается, но хуже расширяется и не даёт естественной уникальности значений. Альтернатива с JSON-колонкой хуже проверяется ограничениями БД.

### 2. Отметка хранит часть дня с sentinel-значением для общего режима

В `tracker_habit_completions` добавляется NOT NULL-колонка `time_of_day VARCHAR(16)` со значением по умолчанию `ANY`:

- `ANY` — общая отметка активности без частей дня;
- `MORNING`/`DAY`/`EVENING` — отметка конкретной части дня.

Существующий уникальный ключ `(habit_id, completed_on)` заменяется на `UNIQUE (habit_id, completed_on, time_of_day)`, а check-ограничение допускает только `ANY`, `MORNING`, `DAY`, `EVENING`. Существующие строки получают `ANY`.

Sentinel выбран вместо nullable-колонки с частичными уникальными индексами, потому что тесты используют H2 в режиме PostgreSQL и должны проходить ту же миграцию, что и production. Nullable-колонка с обычным уникальным ключом допускала бы дубли общих отметок, а `NULLS NOT DISTINCT` недоступен в H2.

На уровне Java-модели `timeOfDay` имеет тип `TimeOfDay` и допускает `null` для общего режима; сервис преобразует `null` ↔ `ANY` при записи и чтении. Отметки остаются в той же таблице, поэтому удаление активности по-прежнему каскадно удаляет всю историю, а статистика и импорт используют один репозиторий.

### 3. API расширяется обратно совместимо

- `HabitRequest`/`HabitResponse`: новое поле `timeOfDay` — список частей дня (пустой список, если частей нет). Запросы без поля трактуются как пустой набор.
- `HabitOnDateResponse`: список `timeOfDay` и `completions` — по элементу `{ timeOfDay, completed }` на каждую часть дня. Поле `completed` сохраняется: для активности с частями дня оно истинно, только когда отмечены все её части, для активности без частей дня — как раньше.
- `HabitHistoryEntry`: добавляется nullable-поле `timeOfDay`; для активности с частями дня на каждый запланированный день возвращается по записи на каждую часть, для активности без частей дня — одна запись с `timeOfDay = null`.
- Отметка и отмена: `PUT/DELETE /habits/{id}/completions/{date}?timeOfDay=MORNING`. Параметр обязателен для активности с частями дня и запрещён для активности без частей дня.

Сохранение `completed` и пустого `timeOfDay` по умолчанию позволяет старым данным и запросам работать без миграции, хотя старый веб-клиент не сможет отметить активность, у которой появились части дня.

### 4. Валидация набора частей дня — в сервисе

`HabitService.validateDefinition` дополнительно проверяет: отсутствие `null` в списке, отсутствие повторов. Неизвестные значения enum отклоняются сериализацией Spring (`400`). Максимум три значения обеспечивается самим перечислением и запретом повторов.

При редактировании набор частей дня заменяется, но строки отметок не трогаются. Поэтому снятая часть дня перестаёт отображаться, а её отметки остаются в БД и снова появляются, если часть дня вернуть. Это соответствует требованию не удалять сохранённые отметки при редактировании.

### 5. Сервис работает с ключом «активность + дата + часть дня»

`HabitService` получает вспомогательное представление отметки и группирует отметки по паре `(habitId, timeOfDay)`:

- список на дату: один запрос отметок за дату, затем для каждой активности собираются признаки по её частям;
- история: отметки за диапазон группируются в множество `(date, timeOfDay)`, затем для каждой активности и каждого запланированного дня формируются записи по частям;
- автоматическая отметка прошлого: для каждой прошлой запланированной даты создаётся по отметке на каждую часть дня (или одна общая, если частей нет);
- отметка/отмена: поиск и удаление выполняются по тройке `(habitId, date, timeOfDay)`, где `timeOfDay` преобразуется в `ANY` для общего режима.

Репозиторий получает методы `existsByHabitIdAndCompletedOnAndTimeOfDay`, `deleteByHabitIdAndCompletedOnAndTimeOfDay` и вариант поиска по дате, возвращающий и `timeOfDay`; в запросах общий режим передаётся строкой `ANY`, а не `null`.

### 6. CSV-парсер группирует строки по типу и названию, а вариант превращает в часть дня

Парсер распознаёт вариант без учёта регистра и пробелов: «Утром»/«Утро»/`MORNING`, «Днём»/«День»/«Днем»/`DAY`, «Вечером»/«Вечер»/`EVENING`. Распознанный вариант не входит в название. Нераспознанный непустой вариант по-прежнему добавляется к названию в скобках.

Результат разбора — список `ImportActivity`, где каждая активность содержит:

- тип и итоговое название;
- множество распознанных частей дня;
- строки `ImportActivityLine(timeOfDay, dailyValues)`, где `timeOfDay` равен `null` для строки без варианта.

Строки группируются в `LinkedHashMap` по ключу «тип + название», что сохраняет порядок файла и делает сводку импорта предсказуемой. Если у активности есть хотя бы одна строка с распознанной частью дня, строки с `timeOfDay = null` не создают отметок — иначе нельзя однозначно определить, к какой части отнести значение.

### 7. Импорт передаёт в сервис явные отметки по частям дня

`HabitService.importActivity` принимает набор частей дня для новой активности и список `ImportedCompletion(timeOfDay, date)`. Логика:

- новая активность создаётся с набором частей дня из файла, датой начала первого числа месяца и ежедневной периодичностью;
- существующая активность переиспользуется без изменения расписания и набора частей дня;
- отметка сохраняется, только если дата не в будущем, попадает в расписание и либо активность не имеет частей дня и `timeOfDay == null`, либо `timeOfDay` входит в текущий набор активности;
- отметки для отсутствующих у существующей активности частей дня молча игнорируются — импорт не меняет расписание.

Сводка считает созданные активности после группировки и сохранённые отметки с учётом частей дня.

### 8. Веб-клиент показывает одну строку активности с чекбоксами по частям дня

- `habitOptions.js` получает `TIME_OF_DAY` и `TIME_OF_DAY_OPTIONS` с русскими подписями «Утро», «День», «Вечер» и фиксированным порядком.
- `HabitFormModal` добавляет необязательную группу флажков частей дня; по умолчанию ничего не выбрано, в запрос уходит массив `timeOfDay`.
- `ActivityListTab` рисует для активности один блок с названием и чекбоксами: по одному на часть дня либо один общий. Ключ занятости чекбокса — `id + часть дня`, поэтому части одной активности отмечаются независимо. Переименование передаёт текущий набор частей дня без изменений.
- Новое действие «Время суток» открывает отдельное модальное окно, которое меняет только `timeOfDay`, отправляя остальные поля активности без изменений.
- `trackerApi` добавляет `timeOfDay` в тело создания/обновления и в query-параметр отметки/отмены.
- `StatisticsTab` строит строки по частям дня: для активности с частями — отдельная строка на каждую часть (ключ `id + timeOfDay`), для активности без частей — одна строка. Группировка по типу сохраняется, подпись строки содержит название и часть дня, статусы берутся из записей истории с соответствующим `timeOfDay`.

### 9. Миграция выполняется одной версией Flyway

Новая миграция `V4__add_tracker_habit_time_of_day.sql`:

1. создаёт `tracker_habit_time_of_day`;
2. добавляет в `tracker_habit_completions` колонку `time_of_day` со значением по умолчанию `ANY`, заполняет ею существующие строки и ставит NOT NULL и check-ограничение;
3. удаляет старый уникальный ключ `(habit_id, completed_on)`;
4. создаёт уникальный ключ `(habit_id, completed_on, time_of_day)`.

Существующие строки отметок получают `time_of_day = 'ANY'` и продолжают работать как общие отметки. Существующие активности получают пустой набор частей дня.

## Risks / Trade-offs

- **Старый веб-клиент не сможет отметить активность с частями дня** → ответы сохраняют поле `completed`, а backend и frontend деплоятся вместе; старые активности без частей дня работают по-прежнему.
- **Снятие части дня оставляет «скрытые» отметки в БД** → это осознанный компромисс ради требования не удалять историю; при возврате части дня история восстанавливается, при удалении активности всё удаляется каскадом.
- **Строки CSV с распознанной частью и без варианта для одной активности** → строки без варианта не создают отметок, чтобы не угадывать часть дня; поведение зафиксировано в спецификации.
- **Sentinel `ANY` протекает в модель** → преобразование `null` ↔ `ANY` сосредоточено в `HabitService`, наружу и в API отдаётся `null`, а значение `ANY` не принимается из запросов.
- **Уникальность обеспечивается миграцией, а не JPA-аннотацией** → сервис дополнительно проверяет существование пары перед вставкой, гонки ограничены уникальным ключом БД.

## Migration Plan

1. Применить миграцию `V4` вместе с обновлённым backend; старые данные совместимы.
2. Задеплоить веб-клиент; новые поля читаются из ответов, старые активности отображаются как раньше.
3. Откат: вернуть предыдущую версию backend и frontend. Миграция обратима вручную удалением колонки, таблицы и индексов; данные отметок при откате схемы теряют только привязку к частям дня.
