## Context

См. `proposal.md` — Why. Текущее состояние, влияющее на подход:

- Сервис `finance` (Spring Boot, `/finances`) имеет слои `category`, `operation`, `balance`, `web`; контроллеры принимают `Long userId` из атрибута, который проставляет `UserIdFilter` по заголовку `X-User-Id`. См. `CategoryService`, `OperationService`, `OperationController`.
- Категория хранит `type` (`INCOME`/`EXPENSE`), `name`, `groupName`, `plannedAmount`, `sortOrder`. Операция хранит `categoryId`, `operationDate`, `amount`; уникальность гарантируется логикой `OperationService.save` (upsert по паре «категория + дата»), а не БД.
- В `finance` нет библиотеки для разбора CSV (в `pom.xml` только webmvc, data-jpa, postgresql, flyway, тестовые).
- Gateway (`ProxyRoutingFilter`) проксирует запросы, буферизуя тело запроса в `byte[]` и пересылая заголовки (кроме blocklist). `Content-Type` (включая `boundary` для multipart) форвардится, `Content-Length` пересчитывается `RestClient`. Значит multipart-загрузка пройдёт через существующий маршрут `/finances` без изменений маршрутизации.
- Веб-клиент использует общий `request()` в `client.js`, который сериализует тело как JSON; для файла нужен отдельный вызов с `FormData` и теми же заголовками авторизации и CSRF (`X-XSRF-TOKEN`).
- Файл-образец `Деньги.csv`: два раздела, статьи с колонками (первый столбец — группа с переносом вниз, второй — название статьи, третий — план за месяц, далее — дни 1..31), запятая как разделитель и как десятичный разделитель, суммы могут содержать пробелы-разделители тысяч.

## Goals / Non-Goals

**Goals:**

- Импорт CSV за выбранный месяц одним запросом: разбор, автоматическое создание отсутствующих категорий, заполнение операций по дням.
- Атомарность: ошибка импорта не оставляет частичных данных.
- Прозрачный результат (сколько категорий создано и операций записано/обновлено).
- Отсутствие изменений схемы БД и минимальные зависимости.

**Non-Goals:**

- Не импортируем строки остатка («остаток с прошлого месяца», «остаток на конец месяца») и не меняем начальный баланс.
- Не удаляем и не «обнуляем» существующие операции и категории, отсутствующие в файле.
- Не поддерживаем произвольные форматы CSV, отличные от выгрузки Google Таблиц на русском языке (иное расположение колонок, точка как десятичный разделитель и т. п.).
- Не меняем порядок (`sortOrder`) существующих категорий.

## Decisions

### Разбор файла на сервере `finance`

Решение: новый мультипарт-эндпоинт `POST /imports` в сервисе `finance`.

- Параметры запроса (`multipart/form-data`): `file` (файл), `year` (число), `month` (1..12). Месяц и год задаёт клиент, из файла они не выводятся.
- Альтернатива (парсинг на клиенте) отклонена: серверный разбор централизует правила, тестируется unit-тестами и переиспользует сервисы `finance` с их валидацией и изоляцией по пользователю.

### Минимальный собственный CSV-парсер

Решение: реализовать небольшой парсер, поддерживающий разделитель-запятую, поля в двойных кавычках и экранированные кавычки (`""`), с обрезкой пробелов.

- Альтернатива (добавить Apache Commons CSV / opencsv) отклонена: формат известен и узок, новая зависимость не оправдана. При усложнении формата решение пересматривается.

### Распознавание структуры

- Разделы определяются по первой непустой ячейке строки: «Статьи доходов» → `INCOME`, «Статьи расходов» → `EXPENSE`.
- После заголовка раздела читаются строки статей. Строка считается статьёй, если хотя бы одна из первых двух ячеек непуста; строки, где обе пусты (итоговые строки и пустые строки), пропускаются.
- Группа переносится вниз до первой непустой первой ячейки в пределах раздела; при смене раздела перенос сбрасывается.
- Колонки (0-based): `0` — группа, `1` — название статьи, `2` — план за месяц, `5..35` — дни `1..31`. Значение дня `d` берётся из индекса `4 + d`.

### Сопоставление и создание категорий

- Ключ сопоставления — тройка (тип, нормализованное название, нормализованная группа), где пустая строка приводится к `null`.
- Существующие категории пользователя читаются один раз и складываются в карту по ключу. Совпадение переиспользуется, отсутствующее создаётся через `CategoryService.create` (получает корректный `sortOrder`).
- План из файла: строго больше нуля → передаётся в `plannedAmount`; пусто/ноль → `null`, что для новой категории означает «без плана», а для существующей — «не менять».

### Заполнение операций

- Для каждого дня месяца и статьи с суммой строго больше нуля вызывается `OperationService.save(userId, request)`, который уже реализует upsert по паре «категория + дата» и валидацию суммы (`> 0`, `<= 2` знака).
- Суммы нормализуются: удаляются пробелы, запятая заменяется точкой, результат парсится в `BigDecimal`.
- Колонки дней, отсутствующих в выбранном месяце, игнорируются.

### Атомарность и результат

- Метод сервиса импорта помечен `@Transactional`: любое исключение откатывает созданные в рамках запроса категории и операции.
- Ответ — `ImportResultResponse(createdCategories, savedOperations)`.

### Клиент и gateway

- Веб-клиент добавляет в `financeApi` метод, отправляющий `FormData` (`file`, `year`, `month`) через `fetch` с заголовками `Authorization` и `X-XSRF-TOKEN` (общий `request()` не используется, т.к. он сериализует JSON).
- Импорт вызывается кнопкой в шапке страницы финансов рядом с действием изменения начального баланса. Кнопка открывает отдельный компонент-модальное окно (`ImportFormModal`) по образцу `BalanceFormModal`: выбор месяца/года (по умолчанию текущий месяц), выбор файла, индикация загрузки и сводка результата. Состояние импорта живёт в модальном окне и `FinancesPage`, а не во вкладке «Статистика».
- После успешного импорта `FinancesPage` перечитывает баланс и увеличивает версию данных, передаваемую во вкладки, чтобы открытая вкладка «Статистика» перезапросила операции (по аналогии с `onOperationSaved`).
- Изменения маршрутизации gateway не требуются. При необходимости поднимается лимит загрузки (`spring.servlet.multipart.max-file-size`), по умолчанию достаточно для CSV.

## Risks / Trade-offs

- [Собственный CSV-парсер может ошибаться на нестандартных данных] → покрыть unit-тестами реальный файл `Деньги.csv`, кавычки, запятые внутри значений и пробелы-разделители.
- [Жёсткая привязка к русским заголовкам разделов и расположению колонок] → при несоответствии структуры возвращать понятную ошибку валидации и не менять данные; формат зафиксирован в спецификации.
- [Дубли статей в файле с одинаковым ключом] → они схлопываются в одну категорию; при совпадении дня побеждает последнее значение (естественный upsert).
- [Много операций в одной транзакции] → объём одного месяца невелик; при росте нагрузок импорт можно разбить батчами (вне рамок этой задачи).
- [Ошибка на середине импорта] → `@Transactional` гарантирует откат; частичных данных не остаётся.

## Migration Plan

- Схема БД не меняется, миграции Flyway не требуются.
- Деплой: обновить образ `finance` и `web`; `gateway` и `postgres` без изменений.
- Откат: вернуть предыдущие образы `finance`/`web`. Импортированные ранее данные автоматически не удаляются — при необходимости их удаляет пользователь вручную.
