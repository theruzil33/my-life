## Context

См. `proposal.md` — Why. Текущее состояние, влияющее на подход:

- Сервис `tracker` (Spring Boot, контекст `/tracker`, порт 8081) имеет слой `habit` с сущностями `Habit` (поля `userId`, `type` `HABIT`/`TASK`, `name`, `startDate`, `frequency`, `weekdays`) и `HabitCompletion` (`habitId`, `completedOn`), сервисом `HabitService` и контроллером `HabitController` (`/habits`). `userId` проставляет `UserIdFilter` по внутреннему заголовку `X-User-Id`.
- `HabitService.markCompleted` валидирует дату отметки: не в будущем, не раньше `startDate`, соответствует периодичности; повторная отметка не создаёт дубликат (`existsByHabitIdAndCompletedOn`).
- В `tracker` нет библиотеки для разбора CSV (`pom.xml` содержит только webmvc, data-jpa, postgresql, flyway, тестовые).
- В сервисе `finance` уже реализован аналогичный импорт (`add-finance-csv-import`): собственный `CsvParser` (package-private), парсер выгрузки, `ImportService` с `@Transactional`, `ImportController` (`POST /imports`), DTO `ImportResultResponse`. Это прямой образец структуры и стиля.
- Gateway (`ProxyRoutingFilter`) проксирует `/tracker` на tracker, буферизуя тело запроса; multipart с `boundary` форвардится, `Content-Length` пересчитывается. Изменения маршрутизации не требуются.
- Веб-клиент: `request()` в `client.js` уже поддерживает `FormData` (не выставляет `Content-Type`), используется в `financeApi.importFile`. Страница `TrackerPage` содержит вкладки `HabitsTab`, `TasksTab`, `StatisticsTab`, каждая из которых сама загружает данные через `trackerApi`.
- Файл-образец `Продуктивность.csv`: первая строка — заголовок с днями 1..31, вторая строка — итоги по дням, далее строки активностей. Колонки (0-based): `0` — название активности (пусто — продолжение предыдущего названия), `1` — вариант/время («Утром», «Вечером», «На работе», «Дома»), `2` — тип («Привычка»/«Задача»), `3..33` — дни 1..31 (день `d` в индексе `2 + d`). Значения дней — `0`, `1` или пусто.

## Goals / Non-Goals

**Goals:**

- Импорт CSV за выбранный месяц одним запросом: разбор, автоматическое создание отсутствующих активностей, заполнение отметок выполнения по дням.
- Переиспользование существующих активностей по паре «тип + название» без изменения их расписания.
- Атомарность: ошибка импорта не оставляет частичных данных.
- Прозрачный результат (сколько активностей создано и отметок сохранено).
- Отсутствие изменений схемы БД и новых зависимостей.

**Non-Goals:**

- Не импортируем строку итогов и строку заголовка как активности.
- Не удаляем и не «обнуляем» существующие активности и отметки, отсутствующие в файле.
- Не поддерживаем произвольные форматы CSV (иное расположение колонок, другие названия типов).
- Не меняем дату начала, периодичность и тип существующих активностей.
- Не создаём отметки на будущие дни и на дни вне расписания активности.

## Decisions

### Серверный разбор в сервисе `tracker`

Решение: новый мультипарт-эндпоинт `POST /imports` (с учётом контекста — `/tracker/imports`).

- Параметры (`multipart/form-data`): `file`, `year` (число), `month` (1..12). Месяц и год задаёт клиент.
- Альтернатива (разбор на клиенте) отклонена: серверный разбор централизует правила, покрывается unit-тестами и переиспользует сервисы `tracker` с их валидацией и изоляцией по пользователю.

### Минимальный собственный CSV-парсер

Решение: использовать небольшой собственный парсер с разделителем-запятой, поддержкой полей в двойных кавычках, экранированных кавычек (`""`) и обрезкой пробелов — как в `finance` (класс в новом пакете `importing`, т.к. `finance.CsvParser` package-private).

- Альтернатива (добавить Apache Commons CSV / opencsv) отклонена: формат известен и узок, новая зависимость не оправдана.

### Распознавание структуры

- Строка считается строкой-активностью, если её тип (`2`) равен «Привычка» или «Задача». Прочие строки (заголовок, итоги, пустые) пропускаются.
- `Привычка` → `ActivityType.HABIT`, `Задача` → `ActivityType.TASK`.
- Название активности: если значение колонки `0` непустое — это базовое название и оно запоминается как текущее; если пустое — берётся текущее базовое название из предыдущей строки.
- Вариант (`1`): если непустой, итоговое название = `базовое название + " (" + вариант + ")"`; если пустой — итоговое название равно базовому.
- Значения дней: день `d` в индексе `2 + d`, где `d` от 1 до 31; колонки за пределами длины выбранного месяца игнорируются.
- Значение дня разбирается в `BigDecimal` (с удалением пробелов-разделителей и заменой запятой на точку, как в `finance`); непустое неразбираемое значение — ошибка импорта.

### Сопоставление и создание активностей

- Ключ сопоставления — пара (тип, итоговое название).
- Существующие активности пользователя ищутся по паре (тип, название); при нескольких совпадениях берётся активность с наименьшим `id` (дубликат не создаётся).
- Новые активности создаются с `startDate` = первое число выбранного месяца и `frequency` = `DAILY`. Существующие активности переиспользуются без изменения их полей.
- Сопоставление выполняется через `HabitService`, чтобы сохранить изоляцию по пользователю.

### Сохранение отметок

- Отметка создаётся для каждого дня месяца, где значение строго больше нуля, при одновременном выполнении условий: `> 0` по значению, день в пределах длины месяца, день не позже сегодняшней даты в настроенном поясе сервиса (`Clock`), день соответствует расписанию активности (`Habit.isScheduledOn`).
- Для новых ежедневных активностей с началом 1-го числа расписанию соответствуют все прошедшие и сегодняшний день месяца.
- Сохранение идемпотентно: перед вставкой проверяется отсутствие отметки на пару «активность + дата» (`existsByHabitIdAndCompletedOn`), повторная отметка не создаёт дубликат.
- Планируются добавочные методы слоя `habit`: поиск активностей пользователя по паре (тип, название) и операция добавления отметок импорта, инкапсулирующая проверки расписания и идемпотентность. Отметки сохраняются через `HabitCompletionRepository`.

### Атомарность и результат

- Метод сервиса импорта помечен `@Transactional`: любое исключение откатывает созданные в рамках запроса активности и отметки.
- Ответ — `ImportResultResponse(createdActivities, savedCompletions)`.

### Клиент и gateway

- Веб-клиент добавляет в `trackerApi` метод `importFile`, отправляющий `FormData` (`file`, `year`, `month`) через общий `request()` (он уже корректно обрабатывает `FormData` и добавляет `Authorization` и `X-XSRF-TOKEN`).
- Импорт вызывается кнопкой в шапке `TrackerPage` рядом с заголовком; кнопка открывает отдельный компонент-модальное окно `ImportFormModal` по образцу `finances/ImportFormModal`: выбор месяца/года (по умолчанию текущий месяц), выбор файла, индикация загрузки и сводка результата.
- После успешного импорта `TrackerPage` инкрементирует версию данных и передаёт её во вкладки (`HabitsTab`, `TasksTab`, `StatisticsTab` через `ActivityListTab` и `StatisticsTab`), чтобы открытая вкладка перезапросила данные. Это требует добавить необязательный проп-ключ обновления в затронутые компоненты вкладок.
- Изменения маршрутизации gateway не требуются. При необходимости поднимается лимит загрузки (`spring.servlet.multipart.max-file-size`), по умолчанию достаточно для CSV.

## Risks / Trade-offs

- [Собственный CSV-парсер может ошибаться на нестандартных данных] → покрыть unit-тестами реальный файл `Продуктивность.csv`, строки-продолжения, варианты и пустые значения.
- [Жёсткая привязка к русским типам и расположению колонок] → при несоответствии структуры возвращать понятную ошибку валидации и не менять данные; формат зафиксирован в спецификации.
- [Дубли активностей в файле с одинаковым ключом] → они схлопываются в одну активность; при совпадении дня отметка не дублируется (идемпотентность).
- [Существующая активность с несовместимым расписанием] → дни вне её расписания не отмечаются, расписание не меняется; поведение зафиксировано в спецификации.
- [Будущие дни в текущем месяце] → пропускаются без ошибки, что соответствует запрету отметки на будущее.
- [Ошибка на середине импорта] → `@Transactional` гарантирует откат; частичных данных не остаётся.

## Migration Plan

- Схема БД не меняется, миграции Flyway не требуются.
- Деплой: обновить образ `tracker` и `web`; `gateway` и `postgres` без изменений.
- Откат: вернуть предыдущие образы `tracker`/`web`. Импортированные ранее данные автоматически не удаляются — при необходимости их удаляет пользователь вручную.
