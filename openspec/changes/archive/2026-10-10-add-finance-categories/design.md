## Context

См. `proposal.md` — Why. В `backend/finance` уже есть вертикальный срез по счетам: сущность `account/Account` (`finance_accounts`), `AccountRepository`, `AccountService`, `AccountController`, `UserIdFilter` (заголовок `X-User-Id`, атрибут `finance.userId`) и `GlobalExceptionHandler` с `ApiError`. Flyway использует `baseline-version=1`; по этому изменению уже добавлена таблица категорий миграцией `V3__create_finance_categories_table.sql`. Gateway проксирует префикс `/finances` в сервис финансов и проставляет `X-User-Id`, дополнительных маршрутов не требуется.

На веб-клиенте `src/pages/FinancesPage.jsx` уже имеет вкладки «Счета»/«Категории»; логика счетов вынесена в `src/finances/AccountsTab.jsx`, категорий — в `src/finances/CategoriesTab.jsx`; парные модальные окна категорий и методы `financeApi` реализованы. Запросы к API финансов идут через `src/api/client.js` (`request`, `requiresAuth: true`, CSRF для изменяющих методов).

## Goals / Non-Goals

**Goals:**

- Дать пользователю возможность объединять категории в именованные группы, указывая название группы в форме категории.
- Отображать категории на вкладке «Категории» визуально сгруппированными, сохраняя текущий порядок «приход → уход» и цветовое различие типов.
- Сохранить принцип «группы — только для визуала»: группировка не меняет контракт логики, работающей с категориями.

**Non-Goals:**

- Не моделировать отдельную сущность группы, её идентификатор, создание/переименование/удаление групп или ссылочную целостность.
- Не менять существующие контракты счетов, аутентификацию и маршрутизацию gateway.
- Не давать логике (будущим операциям) доступ к группам: они остаются меткой отображения.

## Decisions

1. **Группа хранится как необязательное строковое поле категории.** В `finance_categories` добавляется `group_name VARCHAR(200) NULL`; в сущности `Category` — поле `groupName`. Отдельная таблица/сущность группы не вводится. Альтернатива «таблица групп + FK» отклонена: пользователь явно указал, что группа — только название и нужна лишь для визуала, а будущая логика работает только с категориями.

2. **Новая миграция `V4__add_group_name_to_finance_categories.sql`, а не правка `V3`.** Миграция `V3` уже применена в запущенной БД; правка уже применённой миграции сломала бы проверку контрольной суммы Flyway. `V4` добавляет колонку `group_name` через `ALTER TABLE finance_categories ADD COLUMN group_name VARCHAR(200)`. Альтернатива «переписать `V3`» отклонена из-за Flyway checksum.

3. **Контракт расширяется полем `group`.** Тело `POST`/`PUT` — `{ "type", "name", "group" }`, ответ — `{ "id", "type", "name", "group" }`; `group` — строка или `null`. Сервис нормализует группу: обрезает окружающие пробелы, а пустую строку после обрезки трактует как отсутствие группы (`null`). Тип при редактировании по-прежнему игнорируется.

4. **Четыре эндпоинта без изменений: `POST /categories`, `GET /categories`, `PUT /categories/{id}`, `DELETE /categories/{id}`.** `PUT` теперь меняет название и группу (тип неизменен). Поиск/удаление/редактирование идут через `findByIdAndUserId`, поэтому чужая и несуществующая категория дают `404`. Валидация: тип обязателен и входит в enum, название непустое, группа необязательна.

5. **Собственные исключения и общий фильтр.** `category/InvalidCategoryDataException` (`400`) и `category/CategoryNotFoundException` (`404`) уже зарегистрированы в `GlobalExceptionHandler`; `UserIdFilter` переиспользуется как есть.

6. **Порядок сортировки на бэкенде не меняется.** `CategoryService.list` сортирует `INCOME` перед `EXPENSE`, внутри типа — по возрастанию `id`. Группировка MUST NOT требоваться от API: сервис возвращает плоский список, а блоки строит клиент.

7. **Группировка выполняется на клиенте.** `CategoriesTab` строит визуальные блоки из плоского ответа API: для каждого типа (`INCOME`, затем `EXPENSE`) категории с одинаковым непустым `group` собираются в один блок с заголовком; категория без группы образует отдельный блок без заголовка. Блоки упорядочиваются по первому появлению их первой категории в ответе API, категории внутри блока — в порядке ответа API. Тип-скоуп обеспечивается разбиением по типам: блок не смешивает приход и уход. Альтернатива «группировать на сервере» отклонена: группы не часть логики, и API не должен знать о порядке групп.

8. **Ввод группы в форме категории.** Поле «Группа» — необязательный текстовый ввод со списком подсказок (`datalist`) из существующих непустых названий групп категорий выбранного типа; можно выбрать существующее или ввести новое. Модальное окно создания содержит тип, название и группу; модальное окно редактирования — название и группу, а тип показывается только для чтения и не изменяется. `financeApi.createCategory` передаёт `{ type, name, group }`, `financeApi.renameCategory` → редактирование передаёт `{ name, group }`.

9. **Стили.** Существующие классы `category-item-income`/`category-item-expense` (цвет названия) сохраняются; блок именованной группы оформляется контейнером (`category-group`) с той же рамкой (граница, радиус, отступы), что и `.category-item`, чтобы группа выглядела как элемент категории; заголовок группы — `category-group-title`. Промежуток между типом прихода и ухода сохраняется.

## Risks / Trade-offs

- **[Risk]** Правка уже применённой `V3` сломала бы Flyway. **Mitigation:** группа добавляется отдельной миграцией `V4`.
- **[Risk]** Группа — строковый ярлык на каждой категории, поэтому переименование группы в одной категории не переименовывает одноимённые группы у других категорий. **Mitigation:** это осознанное следствие модели «группа — только название»; отдельной сущности группы и массового переименования нет.
- **[Risk]** API допускает одинаковое название группы у категорий разных типов, хотя визуально группы тип-скоупные. **Mitigation:** разбиение по типам на клиенте не даёт смешать типы в одном блоке; сервис намеренно не проверяет это (Non-Goal).
- **[Risk]** Поле группы на клиенте может расходиться с серверной нормализацией (пробелы). **Mitigation:** сервер — источник истины и нормализует значение; клиент показывает ответ сервера после сохранения.
- **[Risk]** Часть уже реализованного кода и тестов описывает «переименование» только названия. **Mitigation:** изменение контракта и UI требует правок в коде; перевести дельту в код — задача `/opsx-apply`.
- **[Risk]** Дубли названий категорий и групп неразличимы на глаз. **Mitigation:** допустимо по решению пользователя; идентификатор категории в ответах API адресует запись однозначно.

## Migration Plan

1. Задеплоить `finance` с миграцией `V4__add_group_name_to_finance_categories.sql` (добавляет `group_name`) и поддержкой поля `group` в контракте. Существующие категории получают пустую группу; поведение счетов не меняется.
2. Задеплоить `web` с полем группы в формах и визуальной группировкой на вкладке «Категории».

Откат: убрать визуальную группировку и поле группы в формах, вернуть `financeApi` к прежним телам запросов и удалить обработку `group` в сервисе. Колонка `group_name` остаётся в БД (не используется).
