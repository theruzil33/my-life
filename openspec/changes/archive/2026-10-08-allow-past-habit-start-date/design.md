## Context

См. `proposal.md` — Why. Текущее поведение «дата начала только сегодня или в будущем» реализовано в трёх местах:

- `backend/tracker/.../habit/HabitService.java:119` — `validateDefinition` бросает `InvalidHabitDataException`, если `startDate.isBefore(today())`; правило общее для создания и редактирования.
- `client/web/src/tracker/validation.js:13` — `validateHabitForm` добавляет ошибку, если `today > startDate`.
- `client/web/src/tracker/HabitFormModal.jsx:100` — у поля даты начала атрибут `min={today}`.

Дата начала — обычная колонка `tracker_habits.start_date` (`LocalDate`), отдельной валидации на уровне БД нет. «Сегодня» на бэкенде определяется `Clock` в настроенном часовом поясе сервиса, на фронте — локальная дата браузера.

## Goals / Non-Goals

**Goals:**

- Инвертировать правило даты начала: `startDate <= today` (сегодня или прошлое), будущее запрещено.
- Согласованно изменить бэкенд и веб-клиент.
- Сохранить остальные правила трекера без изменений.

**Non-Goals:**

- Не менять правила отметки/отмены выполнения, списка на дату, истории и статистики (в том числе запрет будущих дат для просмотра и отметок).
- Не мигрировать и не удалять уже существующие привычки с будущей датой начала.
- Не добавлять интерфейс редактирования привычки (его в вебе нет).

## Decisions

1. **Правило валидации на бэкенде.** В `validateDefinition` заменить проверку `request.startDate().isBefore(today())` на `request.startDate().isAfter(today())` с сообщением вида «Habit start date must not be in the future». Так как метод общий, правило автоматически применяется и к созданию, и к редактированию.

   Альтернатива — отдельная ветка валидации только для создания — отклонена: правило должно быть единым, иначе поведение создания и редактирования разойдётся.

2. **Валидация на фронте.** В `validateHabitForm` заменить условие ошибки на `isAfter(startDate, todayIso())` и текст сообщения на «Дата начала не может быть позже сегодняшней». На поле даты начала заменить `min={today}` на `max={today}`. Значение по умолчанию (`todayIso()`) остаётся.

   Атрибут `max` — вспомогательный: браузерные поля даты позволяют ввести значение вручную, поэтому единственным источником истины остаётся `validateHabitForm` на фронте и валидация трекера на бэкенде.

3. **Представление дельты в OpenSpec.** Требования «Создание привычки» (`tracker-habits`) и «Создание привычки через модальное окно» (`web-tracker`) пересоздаются через `## REMOVED Requirements` + `## ADDED Requirements`, а не `MODIFIED`. Причина: правило инвертирует смысл двух сценариев (будущее → отклонять, прошлое → принимать), то есть их имена должны измениться, а OpenSpec не позволяет переименовывать или удалять существующие сценарии внутри `MODIFIED` (`openspec validate`/`archive` это блокируют). Требование «Редактирование привычки» меняет только содержимое сценария с общим именем, поэтому остаётся `MODIFIED`.

4. **Существующие данные.** Привычки с будущей датой начала, созданные до изменения, остаются в БД и продолжают корректно обрабатываться списком/историей (привычка не попадает в списки на даты раньше её старта). Повторное сохранение такой привычки через редактирование с прежней будущей датой будет отклонено — это ожидаемо. Миграция данных не выполняется.

## Risks / Trade-offs

- **[Risk]** В БД остаются привычки с будущей датой начала, хотя новые такие создать нельзя → поведение неоднородно. **Mitigation:** это осознанно; сценарий «Привычка с будущей датой начала не попадает в список» остаётся в спеке `tracker-habits` и продолжает описывать корректное поведение.
- **[Risk]** Пользователь может вручную ввести будущую дату в `input type="date"` вопреки `max`. **Mitigation:** значение проверяется в `validateHabitForm` до отправки и повторно на трекере (возвращает `400`).
- **[Risk]** Расхождение «сегодня» между браузером (локальная дата) и трекером (настроенный пояс) на границе суток. **Mitigation:** поведение не меняется относительно существующего; проверка на бэкенде остаётся авторитетной.

## Migration Plan

1. Задеплоить `tracker` с новым правилом валидации.
2. Задеплоить `web` с обновлённой формой.
3. Миграции БД не требуются.

Откат: вернуть прежнюю ветку валидации в `HabitService` и `validation.js`/`HabitFormModal.jsx`; данные не затрагиваются.
